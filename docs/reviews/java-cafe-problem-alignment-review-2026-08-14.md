## 1. 教材全体の構成とレビュー対象の概要

教材の掲載順は `content/manifest.json`、各章の本文は `content/ch*.json` で管理されている。掲載順とファイル名の番号は一致しない章がある。各JSONは、章情報の下にレッスンを持ち、レッスンには主に次の要素がある。

- 説明文（Markdown、コード、表、SVG図を含む）
- 実行可能なサンプルと期待出力
- 主問題、追加問題、章末問題
- ひな形、公開・非公開テストケース、ヒント、模範解答
- 構文/APIの使用を調べる `sourceChecks`
- クイズ、正答、解説
- 後半では `artifact`、`project`、`runtime-lab`、`preflight`

教材から参照される実習資材は `labs/`、採点・検証は `src/main/java/jq/` と `tools/` にある。今回のレビューでは、本文だけでなく、問題の採点条件、正答、ヒント、実習README、掲載順、前提条件も対象にした。

## 2. 総合評価

**総合: B+。Java基礎編単体はA-相当。**

初学者向け基礎教材としての土台は非常に良い。説明は具体的で、誤りやすい境界を先回りし、サンプル、段階的問題、隠しケース、ヒント、解説が密接に連動している。全サンプルがJava 21で実行でき、モダンJava、文字コード、リソース解放、日時、並行処理などの説明にも丁寧さがある。

一方、全57章を「Javaを初めて学ぶ人の一本道」として見ると、そのままでは高品質な初心者コースとは言い切れない。主因は次の3点である。

1. 表示章番号、ファイル番号、レッスンID、本文中の章参照が混在し、後半で参照先を誤認する。
2. 621問がほぼすべて必須で、基礎修了地点と職業別・製品別の発展トラックが明示的に分離されていない。
3. 後半のDB、CI/CD、フレームワーク、運用、セキュリティでは、実製品の学習目標をMap・文字列・数値計算によるsingle-file模擬問題で評価している箇所が多い。

技術的な重大誤りは見つからなかった。明確な技術的不正確さは局所的で、いずれも修正可能である。**Criticalは0件**。Highは教材参照の一貫性、検証・実行基盤、後半の評価妥当性に集中する。

## 3. 良い点

### 初心者への説明

- 第1章では `class` や `static` を「後で学ぶ外枠」と明示し、未習語で本題を妨げない。
- 抽象概念を先に定義するだけでなく、値・メモリ・参照・処理順をコード、表、図で見せている。
- `==` と `equals`、整数除算、キャスト位置、オートボクシング、例外のcatch順、`String` の不変性など、典型的なつまずきを具体例で扱う。
- ファイル入出力はUTF-8、close、`Files.lines` / `Files.walk`、シンボリックリンクを含むパストラバーサル、atomic moveの限界まで正確に注意しており、特に質が高い。

### 問題とフィードバック

- 通常レッスンはおおむね2問、章末は「基本・組み合わせ・実践」の3問で、直前の知識を再利用する流れが明確。
- 公開例だけに合わせた実装を防ぐ隠しケースが多く、空、0、負数、境界値、重複、順序をよく検査している。
- ヒントは答えを即座に示すより、処理分解、使うAPI、境界条件の順に進むものが多い。
- クイズは用語暗記だけでなく、出力予測、コンパイルエラー、よくある誤解を問う。

### 技術的品質

- Java 21を対象にし、record pattern、pattern matching for switch、virtual threads、Sequenced Collectionsなどの対象バージョンが一致している。
- 「仕様」「慣習」「状況依存の設計判断」を区別しようとする記述が多い。特にDB、HTTP、トランザクション、セキュリティで絶対論を避けている。
- Spring Boot 4.1.0、Quarkus 3.33.3、Jakarta EE 11、Open Libertyの教材方針は、レビュー日時点の公式情報と整合する。製品依存章は今後も定期更新が必要。
- 後半には実PostgreSQL、実HTTP、Maven/JUnit、JFR、Servlet/JPA、Spring Boot、Open Liberty、Quarkus、コンテナ、TLSなどを動かすlabがあり、「実物に触れる」層が用意されている。

### 構成

- Java基礎編の「出力 → 変数 → 計算・入力 → 分岐 → 反復 → 配列 → メソッド → クラス」の順序は自然。
- オブジェクト指向をクラス、カプセル化、継承、ポリモーフィズム、インターフェースへ分けており、一度に詰め込みすぎない。
- 第20章「総仕上げ」は基礎知識を統合する適切な節目になっている。

## 4. 修正が必要な点

以下では、**技術的に明確な誤り**と、**教材改善提案**を区別する。

### F-01 全サンプルが実行時エラーと表示される検証・実行基盤の不具合

- 重要度: **High**
- 分類: その他（検証基盤・学習体験）
- 種別: **明確な不具合**
- 対象ファイル: `src/main/java/jq/runner/ProcessGroupCommand.java`、`tools/verify_solutions.py`
- 対象: 全サンプル実行
- 該当箇所: `ProcessGroupCommand.WRAPPER` の `set -m`、`"$@" &`、`wait`。検証側はsampleのstderrが1文字でもあると失敗扱い。
- 問題点: 非対話bashのjob-control通知 `[1]+ Done "$@"` がstderrへ出るため、正常終了したサンプルを実行時エラーと判定する。既存の厳密検証では確認した全章の全サンプルに同じ誤判定が発生した。
- 初心者に与える影響: 正しいサンプルを実行しても赤いエラーが見える可能性があり、「教材のコードが壊れている」「自分の環境が悪い」と誤解する。教材品質の自動保証も機能しない。
- 修正案: job-control通知を出さずにプロセスグループを作る実装へ変更するか、wrapper由来の通知を子プロセスstderrと分離する。修正後に全360サンプルと全623問題を既存検証で完走させる。
- 修正理由: 独立ランナーでは360/360件が正常であり、教材コードではなく実行ラッパーが原因と切り分けられるため。

### F-02 表示章番号と内部章番号が混在している

- 重要度: **High**
- 分類: 構成 / 表記
- 種別: **明確な一貫性不備**
- 対象ファイル: `content/manifest.json`、複数の `content/ch*.json`、`labs/**/README.md`
- 対象: 後半編全般
- 該当箇所・代表例:
  - `content/ch54-data-messaging.json` は「第46章」でSQL章を参照するが、現在の画面上のSQL章は第30章。
  - `content/ch46-sql-database.json` は後続labを「第24章・第27章・第54章・第55章」と内部IDで参照するが、表示番号は第40章・第43章・第51章・第53章。
  - `content/ch18-modern.json` はsealed classを「第43章」と参照するが、表示番号は第27章。
  - `content/ch21-layers.json` はCDIを「第25章」と参照するが、表示番号は第41章。
  - `labs/jakarta-ee11/data-exercise/README.md` は48-5を「第24章」と記載する一方、同系列のruntime READMEは「第46章」と記載する。
- 問題点: `manifest.json` の掲載位置、`chNN`ファイル名、`NN-M`レッスンID、本文の「第NN章」が同じ意味ではない。しかもREADMEには表示番号で書かれた箇所と内部番号で書かれた箇所が混在する。
- 初心者に与える影響: 指示された章を見つけられず、未習・既習の判断や復習導線を誤る。学習順序の説明への信頼も下がる。
- 修正案: 人が読む参照は原則として **章名 + レッスンID**（例: 「『SQLとリレーショナルデータベース』46-0」）に統一する。表示番号を出す場合はmanifestから生成し、本文へ手書きしない。内部IDの全面変更は進捗データ移行を伴うため、まず参照表記の統一を優先する。
- 修正理由: 掲載順変更に耐える参照形式が必要であり、章名は初心者にも意味が通るため。

### F-03 後半の実務テーマとsingle-file問題の評価対象がずれる

- 重要度: **High**
- 分類: 問題の不備 / 学習目標との整合性
- 種別: **教材改善提案**
- 対象ファイル: 主に `content/ch46-sql-database.json`、`ch52-team-delivery.json`、`ch53-framework-options.json`、`ch60-spring-boot.json`、`ch61-open-liberty.json`、`ch62-quarkus.json`、`ch38-resilience-observability.json`、`ch56-security-api.json`
- 対象: SQL、CI/CD、フレームワーク、可観測性、OAuth/OIDC、OpenAPIなど
- 該当箇所: 全623問中579問（約92.9%）がsingle-file。実labはあるが、トピックごとの評価はMap、文字列分類、閾値計算などの模擬問題に偏る。
- 問題点: 例えば「インデックスや実行計画」「依存関係管理」「フレームワークの設定」「トレース調査」「OIDC境界」を、標準入力から受け取った文字列や数値を処理するだけで合格できる箇所がある。概念確認には使えるが、学習目標である実ツール・設定・障害診断の能力を直接証明しない。
- 初心者に与える影響: Javaのアルゴリズム問題を解けたことを、DB・ビルド・フレームワーク・運用を扱えることと誤認しやすい。実務上の失敗点（設定、起動、接続、ログ、依存、環境差）を経験しない。
- 修正案: 語彙・判断はクイズへ移し、実装力を測る問題はartifact/project/runtime-labへ置き換える。各トピックに「概念理解」「コード」「実環境」のどこまで評価したかを表示する。実labが重い場合も、設定ファイル編集、ログ読解、コマンド結果の判定など、対象成果物に近い形式を使う。
- 修正理由: 問題形式を学習目標と一致させない限り、正答率が習熟度を表さないため。

### F-04 章・レッスンごとの到達目標が構造化されていない

- 重要度: **Medium**
- 分類: 説明不足 / 学習目標との整合性
- 種別: **教材改善提案**
- 対象ファイル: 全 `content/ch*.json`
- 対象: 全章
- 該当箇所: schemaに明示的な `objectives` / `outcomes` がなく、タイトル・導入文・問題から目標を推測する構造。
- 問題点: 多くの章では導入に「ここで学ぶこと」が書かれるが、粒度と表現が統一されていない。「読み終えた」状態と「自力でできる」状態を区別しづらい。
- 初心者に与える影響: 何を覚え、何をコードで再現できれば次へ進んでよいか判断しにくい。後半の広い章では特に迷う。
- 修正案: 各章に2〜5個、各レッスンに1〜3個の観察可能な到達目標を追加する（例: 「`int`同士の除算と`double`除算の出力差を説明し、必要なキャストを書ける」）。各問題・クイズに対応目標IDを付ける。
- 修正理由: 説明、例、問題、評価の対応を機械的にも人手でも監査できるため。

### F-05 必須量が多く、初心者の最短到達点が見えにくい

- 重要度: **Medium**
- 分類: 初心者への配慮 / 構成
- 種別: **教材改善提案**
- 対象ファイル: `content/manifest.json`、全教材
- 対象: 全57章、全623問
- 該当箇所: 必須621問、任意2問。Java基礎編だけで256問。
- 問題点: 反復量は長所だが、必修・補強・挑戦・職種別の区別がほぼない。基礎、JVM、Jakarta EE、3フレームワーク、本番運用、総合演習を一本道に見せると、初学者には終点が遠すぎる。
- 初心者に与える影響: 学習疲労、完璧主義、離脱につながる。どこまでで「Java基礎を修了」と言えるか分かりにくい。
- 修正案: 第20章を明確な「Java基礎修了」マイルストーンにし、章末問題の一部を任意の補強・挑戦へ分ける。その後を「標準API・開発基盤」「バックエンド」「JVM・性能」「運用」などの選択トラックにする。
- 修正理由: 初学者が小さな達成を積み、目的に合う発展先を選べるため。

### F-06 Web編の前提条件が広すぎる

- 重要度: **Medium**
- 分類: 構成
- 種別: **教材改善提案**
- 対象ファイル: `content/manifest.json`
- 対象: Web・Jakarta EE編
- 該当箇所: 「Java実践・開発基盤編とJVM・並行処理・性能編の修了を推奨」
- 問題点: Servlet、HTTP、JDBCへ進むためにJFR、GC診断、デッドロック再現、性能測定まで終える必要があるように読める。実際に土台となるのは例外、コレクション、テスト、SQL、JSON/HTTP、基本的なスレッドセーフであり、性能診断全体ではない。

- 修正理由: 必要な依存だけを前提にすれば、段階性と動機を両立できるため。

### F-07 早い段階に「エラーの読み方・デバッグ」の独立した練習がない

- 重要度: **Medium**
- 分類: 説明不足 / 初心者への配慮 / 構成
- 種別: **教材改善提案**
- 対象ファイル: Java基礎編、`content/ch52-team-delivery.json`
- 対象: 第3〜5章付近、および現在の「デバッグ・計算量・静的解析」
- 該当箇所: コンパイルエラーや例外は各章で説明されるが、診断メッセージの読み順、行番号、stack trace、最小再現、変数の観察を体系的に扱うのは後半。
- 問題点: 初心者が最初に必要とする自己解決技能が、チーム開発・品質管理までまとまって登場しない。
- 初心者に与える影響: 小さな入力ミスや構文エラーで、自力復旧できず学習が止まる。
- 修正案: 第3〜5章の間に短い「エラーを読む」単元を追加し、意図的に壊れたコードを直す問題を置く。例外章でstack traceへ再接続し、後半でデバッガ・計測へ発展させる。
- 修正理由: デバッグは全後続単元の学習効率を支える横断技能であるため。

### F-08 丸め規則を問題文に書かず、HALF_UPだけを正解にしている

- 重要度: **Medium**
- 分類: 問題の不備 / 技術的誤り
- 種別: **明確な問題仕様不足**
- 対象ファイル: `content/ch42-numeric-text.json`
- 対象: 42-5 章末演習の実践問題
- 該当箇所: 「n個の商品価格文字列を…US形式で小数2桁…」という問題。隠し入力に `0.005` があり、模範解答は `RoundingMode.HALF_UP`。
- 問題点: 小数2桁という表示形式だけでは、HALF_UP、HALF_EVENなどの丸め規則は決まらない。問題文とヒントはHALF_UPを指定しないが、期待出力はそれを前提にする。
- 初心者に与える影響: 技術的に妥当な別の丸め方が不正解になり、理由を推測できない。表示桁と丸め規則を同じ概念と誤解する。
- 修正案: 「小数第3位をHALF_UPで丸める」と明記し、`0.005`、負数、HALF_EVENとの差を解説する。または複数の業務ルールを入力・設定として扱う。
- 修正理由: 金額計算では丸め規則は仕様であり、暗黙に決めてはいけないため。

### F-09 ローカル変数は「必ずコンパイルエラー」という正答文

- 重要度: **Medium**
- 分類: 技術的誤り
- 種別: **明確な技術的不正確さ**
- 対象ファイル: `content/ch08-class.json`
- 対象: 8-5 クイズ「初期化していない変数について」
- 該当箇所: 正答選択肢「フィールドは既定値、ローカル変数は必ずコンパイルエラー」
- 問題点: ローカル変数の宣言 `int x;` 自体は合法。definite assignmentにより、代入される前に値を読むとコンパイルエラーになる。直後の解説は正しく「初期化せずに読むと」と書いており、選択肢だけが過剰。
- 初心者に与える影響: 宣言と参照を区別できず、後から代入する正しいコードまで違法だと覚える。
- 修正案: 「フィールドには既定値が入り、ローカル変数は値を代入する前に読むとコンパイルエラー」に変更する。
- 修正理由: Javaのdefinite assignment規則を正確に表せるため。

### F-10 `List.of` / `Set.of` を「完全に不変」と説明している

- 重要度: **Medium**
- 分類: 技術的誤り / 用語
- 種別: **技術的な過度の単純化**
- 対象ファイル: `content/ch16-collection.json`
- 対象: 16-5「Set と、変更できないリスト」およびクイズ
- 該当箇所: 「`List.of(...)` や `Set.of(...)` で作ったコレクションは不変」「完全に不変」
- 問題点: 正確には、要素の追加・削除・置換ができないunmodifiable collectionである。格納した可変オブジェクトの状態は変えられ、深い不変性は保証されない。`List.of` / `Set.of` がnullを拒否する点も、この説明では扱われない。
- 初心者に与える影響: 第9章で学ぶ「参照がfinalでも参照先は可変」という理解と衝突し、コレクションの不変性を過大評価する。
- 修正案: 「コレクションの構造を変更できない」と表現し、要素が可変なら内部状態は変わる例を1つ追加する。「深い不変」と区別し、null不可も短く示す。
- 修正理由: unmodifiableとimmutableはAPI設計で重要な区別だから。

### F-11 `final`フィールドの初期化箇所を限定しすぎている

- 重要度: **Low**
- 分類: 技術的誤り / 説明不足
- 種別: **技術的な省略**
- 対象ファイル: `content/ch09-encapsulation.json`
- 対象: 9-2、および9-4付近のクイズ解説
- 該当箇所: 「`final`フィールドは宣言時または各コンストラクタで初期化」
- 問題点: instance initializerでもblank final instance fieldを初期化できる。static finalにはstatic initializerもある。初心者向けに省略すること自体は妥当だが、可能な場所を列挙し切った表現に見える。
- 初心者に与える影響: 後にinitializerを見たとき、正しいコードを例外や特殊仕様と誤解する。
- 修正案: 「まずは宣言時または各コンストラクタで初期化すると覚えます。initializerでも可能です」と限定を明示する。
- 修正理由: 教える範囲を絞りつつ、誤った一般則にしないため。

### F-12 `TreeSet<String>`を「文字コード順」と表現している

- 重要度: **Low**
- 分類: 表記 / 技術的誤り
- 種別: **技術的な過度の単純化**
- 対象ファイル: `content/ch16-collection.json`
- 対象: 16-5
- 該当箇所: 「`TreeSet` の辞書順は文字コード順」
- 問題点: `TreeSet`は要素のnatural orderingまたはComparatorに従う。`String`のnatural orderingは `String.compareTo` によるUTF-16 code unitの辞書式比較であり、ロケール依存の辞書順ではない。「文字コード順」だけでは補助文字や正規化、言語別照合を誤解させる。
- 初心者に与える影響: 日本語・大文字小文字・アクセントを人間の辞書順で並べられると思い込む。
- 修正案: 「ここではStringのnatural ordering（`compareTo`）順。言語に合う並び替えはCollator等が必要」とする。
- 修正理由: 後続のLocale章との接続が明確になるため。

### F-13 出力だけで十分な問題に、特定の書き方を要求するsourceCheckがある

- 重要度: **Medium**
- 分類: 問題の不備
- 種別: **明確な採点条件不整合の代表例**
- 対象ファイル: `content/ch06-array.json`、共通して全 `sourceChecks`
- 対象: 6-6 章末演習「n個の整数を逆順に半角スペース区切り」
- 該当箇所: 問題文は行末空白を禁止するだけだが、sourceCheckは空の `println()` または `String.join` の出現を必須にする。
- 問題点: 最後の要素だけ `println(value)` にする、`StringBuilder`で組み立てるなど、仕様を満たす正しいコードが不合格になる。教材全体でsourceChecksが587件あり、API・構文が学習目標の問題と、単なる実装手段の制約が混在する。84件はひな形だけで既に満たされるため、学習者がその構文を書いたことの証明にもならない。
- 初心者に与える影響: 出力が正しくても理由の分からない不合格になり、「正解は一つ」と誤解する。
- 修正案: 構文/API自体が到達目標のときだけsourceCheckを使い、問題文へ必須条件を明記する。出力仕様だけが目標ならケース判定へ任せる。各sourceCheckに対応するobjective IDを要求する。
- 修正理由: 技術的に正しい代替解を公平に受け入れつつ、学習構文を必要な場面では確実に評価できるため。

### F-14 `parallelStream`の共通プール説明が断定的

- 重要度: **Low**
- 分類: 技術的誤り / 説明不足
- 種別: **技術的な過度の単純化**
- 対象ファイル: `content/ch40-stream-optional.json`
- 対象: 40-4「一度きり・副作用なしを基本にする」
- 該当箇所: 「ブロックするI/Oを待つと、無関係な並列処理まで止まります」
- 問題点: 共通ForkJoinPoolのworkerがブロックされると、他処理がstarvationや遅延を受け得るが、常に全てが停止するとは限らない。
- 初心者に与える影響: 危険性の方向は正しいが、「必ず停止する」という誤った因果で覚える。
- 修正案: 「共通プールのworkerを占有し、無関係な処理まで遅延・枯渇させることがあります」にする。
- 修正理由: 推奨（ブロッキングI/Oにparallel streamを使わない）を保ちながら、挙動を正確に説明できるため。

### F-15 模範解答の短い変数名が後半で増える

- 重要度: **Low**
- 分類: 初心者への配慮 / 表記
- 種別: **教材改善提案**
- 対象ファイル: 複数の `content/ch*.json`
- 対象: 主に模範解答
- 該当箇所: `Scanner s` がサンプル・解答内に216回。`n`、`a`、`b`、`x`、`w`なども頻出。
- 問題点: 小問では簡潔だが、後半の長い解答でも同じ命名が続き、説明文の丁寧さに対してコードの可読性が下がる。
- 初心者に与える影響: 何を保持する変数か追う負荷が増え、短い名前を一般的な良い慣習と受け取りやすい。
- 修正案: `scanner`、`count`、`values`、`word`、`result`等へ統一する。ループ添字`i`、座標、短いラムダ引数など慣用的な短名は許容する。
- 修正理由: 模範解答は動作だけでなく、読みやすいJavaの手本でもあるため。

   - `String.compareTo`、Comparator、locale-aware collationを区別する（F-12）。
4. **英語語彙の表記**
   - container、image、download、runtimeなど英語をそのまま使う文体と、コンテナ、イメージ、ダウンロード、実行環境という日本語表記が混在する。CLIの固有概念・コマンド名は英語、それ以外は日本語という基準を決める。
5. **コード内の命名**
   - `Scanner sc` と `Scanner s`、説明的な変数名と一文字名が混在する。模範解答では説明的な名前を既定にする（F-15）。
6. **「必ず」「完全に」「止まる」**
   - 条件付きの挙動を断定する語が少数ある。仕様上常に成立する場合だけ使い、それ以外は「起こり得る」「この教材では」にする（F-10、F-11、F-14）。
7. **mini実装と実製品**
   - mini Servlet/CDI/JPA等は学習上有効。各章で「同じ構文」「簡略化した挙動」「実製品でのみ保証されること」を同じラベルで表示すると、章間の粒度が揃う。
