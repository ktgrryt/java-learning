### 1〜5 の検証

出力を主張している箇所は、抽出して実際に実行して突き合わせた。**解説本文の出力ブロックは
`verify-solutions.sh` の対象外**（照合されるのは `samples[].expected` だけ）なので、
1と2はこの穴に落ちていた。抽出できた20組のうち2組が誤りだったので、比率としては小さくない。

将来これを機械で捕まえるなら、解説の ```java``` ブロックと直後の出力ブロックを取り出して
実行照合する検査になる。ただし解説のコードは断片が多く、そのままでは実行できないものが
ほとんどなので、**「実行できる形で書いた組だけを検査する」約束を先に決める**必要がある。

### 6 番号の見え方

原因は、**章参照には読み替えがあるのにレッスン参照には無かった**こと。

- `web/app.js` の `displayLessonId` を、IDの数字ではなく**章の中の位置**から振るようにした。
  事前確認だけは本編に数えず `-0` を割り当てる（`check-chapter-refs.sh` が位置を検査する）
- `localizeLessonReferences` を追加し、本文の `13-5` を画面の番号（`14-5`）へ読み替える。
  **コードブロックの中は読み替えない**（`5-5` の二重ループの出力例が `1-1 1-2 2-1 …` で、
  これはレッスンIDと同じ形をした出力）
- `check_chapter_refs.py` へ、レッスン参照の解決・読み替えの効かないフィールド・
  事前確認の位置の3つを足した。走査対象は**学習者が読む文章だけ**に絞る
  （`expected` や `solution` には `COMMIT 1-3` のようにIDと同じ形の文字列がふつうに出てくる）

画面での確認はChrome DevTools Protocolで15件。番号が1から連番になること、参照が読み替わること、
コードブロックの出力例が壊れないこと、章参照が今までどおり動くことを見た。

### 7 GCの追記

- `30-2`: 「回収できるか」ではなく「いつ止まるか」で見る話、若い領域と全体の回収の違い、
  JDK 21の既定が `G1`（小さい環境では `Serial`）であること、`-XX:+UseZGC` の使いどき。
  **先に見直すのはコレクタではなく上限と割り当て**という順序を「間違えやすい点」に置いた
- `37-3`: `-Xlog:gc*` の付け方（`*` を引用符で囲む。zshでは囲まないと起動しない）と、
  実測した `G1` のログ2行、読むところ4つ（種類・理由・回収前後と上限・止まった時間）。
  この章の問題が使っている簡略化した入力との関係も書いた

ログの行と `Pause Young` の形式は、`-Xlog:gc*` を実際に動かして採った出力に合わせている。

### 8 `ch37` の事前確認

他17章と同じ形で `37-0` を新設し、**章に入る前にlabと同じ判定**を見せるようにした。

- 確認するのは `java` / `javac`（21以上）、`jcmd`、**JFRの記録**の4項目
- JFRは「`jfr` コマンドが在るか」では判定しない。`JdkCapability.canRecordFlight()` で
  **短い記録を実際に作って**確かめる。この判定は `RuntimeLabRunner` からも呼ぶので、
  事前確認は通るのにlabだけ環境不足になる食い違いが起きない
- 本文にHotSpot系とOpenJ9系の違い、`java -version` の2行目の読み方、
  `JQ_JAVA_HOME=/path/to/hotspot-jdk ./run.sh` での回避を書いた。JDKを入れ替える必要はない
- `37-3#2` の問題文にも1文だけ足して、事前確認へ送るようにした
- 事前確認の許可ツールへ `jcmd` と `jfr` を追加（`ContentLoader.PREFLIGHT_TOOLS`）。
  `jcmd -h` は使用方法に数字が混ざるので、版として読まないようにしている

検証は、この端末（Semeru/OpenJ9 25.0.3）で**失敗側の経路**を実際に通した。
`check-preflight-runner.sh` は「事前確認の判定がruntime labの実測と一致すること」と
「任意にすれば準備完了を妨げないこと」を見る。成功側（記録が作れる）は手元にHotSpotのJDK 21以降が
無いため、HotSpot 17で記録ファイルが作られること（361KB）だけを直接確かめた。
ブラウザでは章の先頭（0番目）として並び、実測してJFRだけが落ち、対処が出ることを確認した。

### 9・10 クイズの解説と選択肢

**解説。** この教材の標準は「誤答を1つずつ否定してから、正解の理由を述べる」形で、基礎編は
ほぼ全問がそうなっている。後半（`ch45` `ch50`〜`ch56` `ch60`〜`ch63` `ch65` など）に、
正解の言い換えだけで終わる解説が固まっていた。

- 138問を1問ずつ読み、**92問を書き足した**。残る46問は言い換えで誤答を否定していたので触っていない
  （たとえば「404は対象なし、403は認可拒否、400は入力不正です」は、選択肢の語と重ならないが
  十分に否定している）。**数えた138は過大**で、指標としては目安にしかならない
- `answer` と `choices` は1問も変えていないので、`progress.json` の `quizChoices` は
  そのまま使え、手がかりの指標（長さ・断定語・位置）も動いていない（101問 / 25.2% のまま）
- 標準の形と、機械では判定できないことを `docs/guide.md`「解説は誤答を名指しで否定する」へ書いた

**選択肢。** `63-3` の正解だけは文そのものが反転していた（「2倍にする理由」を問うのに、
選択肢が「2倍にすると下流を倒す」と読める）。条件を補って直し、長さは他の選択肢より短いままに

### 採点が測っていなかったもの

**14 `41-3#1` の `match=true`。** 型を実行時に確かめる問題なのに、`match` 欄が全5ケースで
`true` だった。`type=` 欄は入力で変わるが、`match=true` は書くだけで通るので、
`isInstance` を一度も呼ばずに合格できた。`Class<?>` と `.isInstance(` の検査を足した
（問題文が「`Class<?>` と `isInstance` を使って」と明示しているので、`sourceChecks` の
線引きにも合う）。

**15 `54-6#2`（ch65）の `failed=`。** `SUMMARY running=… done=… failed=…` の `failed` が
全6ケースで0だった。FAILEDで終わる実行が1件も無く、集計の3つ目は未採点だった。
`FINISH … FAIL` で終わるケースを足した。

**16 `47-3#1` の再試行判定。** 問題文は「GET/PUT/DELETEの429,502,503,504だけRETRY」と
決めているのに、ケースは4件で **RETRYは `GET 503` の1点だけ**だった。
`status == 503 && method.equals("GET")` と書いても合格する。PUT 429・DELETE 504・GET 502・
POST 429・GET 500 を足して9件にした。
（`47-5#2` は8件あり429/503とPUT/DELETE/POSTを押さえているが、502と504は入力に出ない。）

**17 `22-6#3` の「アンパサンド」。** 入力が `GET /search?q=a&b` で、`&` はHTTPの
パラメータ区切りとして解釈される。`q` の値は `a` だけになり、期待出力も `検索: a` なので、
**`&` → `&amp;` の変換を一度も確かめていなかった**（ラベルだけが確かめたと言っていた）。
同じ章の `22-5#1` は `%26%3C%3E%22%27` と符号化して正しく確かめている。入力を `q=%26b`、
期待出力を `検索: &amp;b` に直した。
