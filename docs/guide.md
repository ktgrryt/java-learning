# Java Café 詳細ガイド

[短いREADMEへ戻る](../README.md)

この文書には、画面の詳しい使い方、カリキュラム、教材の編集方法、検証手順、内部構成をまとめています。

手を動かしながらJavaを学ぶための、ローカルで動く学習アプリです。

レッスンは **具体例つきの解説 → その場で実行できるサンプル → 自動採点される練習問題** の3段構えです。
基礎〜標準APIの章では通常2問、章末演習3問を基本とし、外部システムを扱う章では
アプリ内の問題に加えて `labs/` の実測手順で学びます。
書いたコードを提出すると隠しテストを含む全ケースで自動採点され、全部通ると ★ が付きます。

**★ は必須問題ごと（全664問）に付きます。** このほかに章クリアへ影響しない任意発展問題が2問あります。
提出課題を持たない**概念レッスン**（16レッスン）だけは、確認クイズに全問正解すると★が1つ付きます
（「概念レッスンを書く」）。★の総数は 664 + 16 = 680 です。通常レッスンの2問目は、解説が教えているのに1問目では手を動かさない
論点をピンポイントで問う **応用問題**です（`5-2` なら、1問目の「合計をためる」に対して
解説にだけ出てくる「掛け算をためる＝階乗」を書きます）。
読む量と書く量がだいたい 1:1 になるよう、「解説で教えたことには必ず対応するアウトプットがある」
状態を目安に作ってあります。クリアした問題は見出し1行に畳まれるので、ページは伸びません。

**4択の確認クイズ** は全522問で、**章あたり3〜21問**です。全レッスンにあるわけではありません
（最多はシステム開発ライフサイクル編の「開発の全体像と工程」で、★の根拠がクイズだけの概念レッスンを3つ持ちます）。
355レッスンのうち**182レッスン**に1〜6問（多くは2問か4問）まとめて置いてあり、残りのレッスンには0問です。
このうち18レッスンは★対象外の環境事前確認で、16レッスンはクイズだけで★が付く概念レッスンです。
基礎編やWeb編では章の最後の通常レッスンに寄せ、後半の章では各レッスンへ分散させています。
章末演習はほとんどが0問ですが、Java実践・開発基盤編の5章だけは章末演習にも4問ずつ置いています。「このコードはコンパイルできるか」
のように、コードを書く形では出題できない知識を試すためのものです（★ の判定には影響しません）。

**どのレッスンにもいつでも飛べます。** 順番のロックはかけていないので、気になる章から始めても、
分からなくなったら前の章に戻っても構いません。どこまで終わったかはサイドバーで一目で分かります。
各編を選ぶと「学習の前提」が表示されます。初めて学ぶ場合はJava基礎編の第1章から、
後半の編へ進む場合はそこに書かれた編・章を先に終えるのがおすすめです。

画面は3つです。起動時の**学習ホーム**、設備から店舗経営を育てる**カフェ画面**、教材に取り組む**レッスン画面**。
ヘッダーの「📚 学習」「☕ カフェ」で、長いスクロールをせずに2つのメニューを切り替えられます。

**問題を解いている途中でも、気軽にカフェへ寄り道できます。** レッスンからカフェへ移ってアイテムを買ったあと、
「📚 学習」を押すと解いていたレッスンへ、**読んでいた位置のまま**戻ります（書いていたコードもそのままです）。
章を選び直したいときは、カフェ画面の「📚 章を選ぶ」か左上のロゴから学習ホームへ行けます。
自分で学習ホームへ移ってからカフェへ入ったときは、「📚 学習」もこれまでどおり学習ホームへ戻ります。

#### 章の到達状況は3層に分けて出す

選んだ章の右側に、**概念 / コード / 実践** の3つを並べます。★は問題ごとに1つなので、簡略な模型と
実物を動かす課題が同じ見た目になります。何を説明できるのか、何を書けるのか、何を動かして直せる
のかは別の能力なので、分けて示します。

```
┌──────────────┬──────────────┬──────────────┐
│ 概念 ✓       │ コード       │ 実践         │
│ 4 / 4        │ 0 / 9        │ —            │
│ クイズで確かめる│ 書いて動かす │ この章にはありません│
└──────────────┴──────────────┴──────────────┘
```

数え方は問題の種類から決めます。定義は `jq.content.Curriculum#layerProgress` の1箇所だけです
（以前はブラウザ側にも同じ処理があり、2箇所あるとずれるので寄せました）。

| 層 | 数えるもの |
|---|---|
| 概念 | 確認クイズ（概念レッスン以外では★の判定に影響しませんが、知識の確認はここで数えます） |
| コード | `single-file` と `artifact`（コードや設定を書く） |
| 実践 | `project` と `runtime-lab`（実物を起動・観測・修正する） |

任意発展問題（`required: false`）は分母へ入れません。対象が0件の層は達成にしません
（クイズや実践課題を持たない章でバッジだけ点くと、達成の意味が薄れます）。

**達成した層は日付つきで保存します。** 導出だけにすると、章へ問題を足した瞬間に過去の達成が
未達成へ戻ってしまいます。それでは「この章の実践までやり切った」という記録として使えません。
所有アイテムと同じく、一度達成したら消しません（`progress.json` の `layerCompletions`。
キーは `章ID#層`）。いま満たしていない場合は「2026-08-14 に達成（追加分が残り）」のように、
記録と残件の両方を出します。検査は `./tools/check-layer-completion.sh` です。

#### 到達目標も問題を書く側の基準（画面には出さない）

章には**到達目標**（`objectives`）を2〜5個、全69章で283個書いてあります。3層が「どの形式まで
到達したか」を答えるのに対し、こちらは「**何ができるようになるか**」を表します。ただし
**学習者の画面には出しません。** いちど3層の下へ「この章でできるようになること」として並べましたが、
章を選ぶ画面で必要なのは「次に何をするか」であり、未着手の章では `0/4問` が並ぶだけでした
（下のrubricを外したのと同じ理由です）。

出さないかわりに、**問題を書く側の基準**として使います。

- `sourceChecks` で字面を縛ってよいかの判断が、その章の目標に紐づく（「sourceChecks は…」）
- 664問と522クイズが必ずどれかの目標へ解決されることを `./tools/check-objectives.sh` が見張る。
  測る問題の無い目標、どの目標にも紐づかないレッスンを落とす

`/api/state` には `objectives` と `objectiveIds` を出してあるので、別の見せ方をしたくなれば使えます。
章クリアや★の判定は目標と無関係なので、出さなくても進行は変わりません。
書き方は「到達目標を書く」にあります。

#### 実務rubricは問題を書く側の基準（画面には出さない）

**rubric（ルーブリック）** は評価基準表のことです。「何ができたら合格か」を観点ごとに分けて
書いた表を指します。★は問題ごとに1つ付くだけなので、「暗記して書けた」と「壊れたものを直せた」が
同じ見た目になります。観点を分けるのがこの基準の役割です。

**rubricは画面に出しません。** 章の5軸表（☆☆×5＋合計）も、レッスン一覧の軸タグも外しました。
章を選ぶ画面で知りたいのは「次に何をするか」で、採点の内訳ではありません。手を付ける前の章では
☆☆ が5つ並び、「test / 対象なし」「合計 0 / 8」「実装と診断が各1点以上＋8割」だけが読める状態に
なり、行動につながりませんでした。レッスン行のタグも、その表が凡例として無ければ「説明」「診断」が
何を指すのか学習者には分かりません。**章クリアの判定はこの点数と無関係**（★の達成率で決まる）なので、
外しても進行は変わりません。算出は API（`ApiHandler.chapterRubric` / `lessonRubric`）に残してあります。

**残っているのは、問題を書く側の基準としての役割です。** どの問題がどの能力を測るかを決めるのは
出題側の設計判断で、それが無いと「診断まで扱う章」と「実装だけの章」の区別が付かなくなります。
以下は外した表の仕様として残します。

```
┌──────┬──────┬──────┬──────┬──────┬──────────────┐
│ 説明 │ 実装 │ 診断 │ test │ 判断 │ 合計         │
│ ★★  │ ★★  │ ★☆  │  —   │ ★★  │ 7 / 8        │
│ 9/9  │ 11/11│ 1/2  │対象なし│ 2/2  │実務修了の条件を満たす│
└──────┴──────┴──────┴──────┴──────┴──────────────┘
```

| 軸 | 意味 |
|---|---|
| 説明 | 対象の役割を自分の言葉で説明できる |
| 実装 | 最小の正常系を実装・起動できる |
| 診断 | 代表的な失敗を再現し、error/logから原因を特定できる |
| test | testで修正を固定できる |
| 判断 | 制約とtrade-offを説明し、選択理由を記録できる |

**軸は問題の型からは決まりません。** `runtime-lab` は「実装」と「診断」の両方を兼ねるものと、
どちらか片方だけのものがあります。そこで問題へ任意の `rubric` 欄を書きます。

```json
"rubric": ["diagnose", "decide"]
```

書かない場合の既定は控えめです。`single-file` と `artifact` は「実装」だけ、`project` と
`runtime-lab` は「実装」と「診断」を主張します。診断や判断まで測っていると言いたい問題には、
明示的に書いてください。

**軸はキーワードで決めないでください。** 「判定してください」で機械的に拾うと、第4章の
「映画館の料金を判定する」（if/elseの練習）まで「判断」になり、rubricが嘘をつきます。
§8.4の定義へ厳しく当てます。

| 軸 | 書く条件 | 書かない例 |
|---|---|---|
| `diagnose` | 証拠（ログ・ダンプ・計測結果）から原因を突き止める | ダンプ形式の入力を集計するだけ／規則を1つ当てるだけ |
| `decide` | 制約のもとで候補から選び、理由を示す | 出力がverdictでも、規則の当てはめなら書かない |
| `test` | テストそのものを書く／テストの範囲を決める | テスト対象の実装を書くだけ |

現在は必須664問のうち**105問**へ書いてあります（`single-file` 56・`runtime-lab` 34・`artifact` 9・
`project` 6）。**全664問を1度は見ているので、`rubric` が無いことは「見たうえで実装のみ」を意味します。**

そのため、**問題を足すときは実装以外の軸を測るかどうかを必ず判断してください。** 書き忘れると、
その能力は集計から抜けます（既定は「実装」だけを主張します）。

点の付け方と、実務修了の判定は次のとおりです（画面には出しませんが、`meetsThreshold` の定義です）。

| 点 | 条件 |
|---|---|
| ★★（2点） | その軸を測る問題を全部クリアした |
| ★☆（1点） | 半分以上クリアした |
| ☆☆（0点） | それ未満 |
| — | その章に**その軸を測る手段が無い**（0点とは区別します） |

実務修了の条件は「合計8割以上、かつ実装と診断が各1点以上」です。ただし **測っていない軸は
条件へ数えません**。クイズしか無い章に診断を要求しても意味がないので、測っている軸だけを
分母にします。`ch01`は説明・実装の2軸だけなので満点で4/4、`ch57`は5軸すべてが対象で10/10です。

**測っていないこと。** 「自分の言葉で説明できる」「選択理由を記録できる」の中身は測れません。
言えるのは「説明を書く課題（クイズ・報告・ADR）を通した」までです。rubricは*何を通したか*の
要約であって、文章や判断の質の評価ではありません。

任意発展問題はどの層の分母にも入れません（章クリアの対象外なので）。実践の課題が残っている章では
注記が「章クリアに必要」に変わります。実践課題は `required` なので、実際に章クリアの条件に入って
います。実践課題を持たない章は `—` と出し、無いことが分かるようにします。

「学習の記録」は ★ / 連続日数 / 通過したテストケース / 実行した回数 / 正解した確認クイズ の
5枚です（上の図は幅の都合で4枚だけ描いています）。

### カフェ画面

問題の初回クリアで得たコイン、累計提供数、購入できる設備をまとめて表示します。
学習ホームとは別ページなので、設備をじっくり選びたいときだけヘッダーの「☕ カフェ」から開けます。
最初は設備だけが表示され、★4で「店舗」が解放されます。「アイテム」は、学習と売上の節目まで進んだとき、
または**特別な達成条件を満たしたとき**に初めて登場します。

設備は「販売戦略・抽出力・イベント・クイズ接客・常連サービス・自動営業」の6系統です。
それぞれ12段階あり、現在の設備を上位互換へ順番に買い替え、下位設備の効果は上位設備の性能へ
置き換わります。
設備画面の「売上・ボーナスの意味」を開くと、正解チップや章ボーナスなどが発生するタイミングと
増える報酬を確認できます。

**設備に★の解放条件はありません。** コインが足りれば、どの系統をどこまで伸ばすかは自由です。
歯止めは価格だけで、Rank1〜5は1段ごとに**約4.2倍**、Rank6〜7は**約5倍**、Rank8以降は
**約6.5〜7.5倍**に上がります（効果の伸びは1段あたり4〜7割なので、上のRankほど1コインあたりの
価値は下がる）。だから「1系統を深く掘る」も「安い段を浅く広く買う」もどちらも成立し、
どちらか一方が正解にはなりません。

以前はRankごとに必要★を決めていましたが、それは「今はこのRankしか買えない」という一本道に
なり、どの系統から育てるかという選択そのものを奪っていました。今★が絡むのは設備ではなく、
店構えLv・店舗の出店枠・終盤改装・アイテムの発見条件だけです（どれも一本道なので選択の幅を
狭めません）。

6系統は**それぞれ別のものを増やします**（同じ数値を取り合う系統はありません）。

| 系統 | 増えるもの |
|---|---|
| 販売戦略 | コインが入るすべての場面の単価（問題・章・クイズのチップ・自動売上） |
| 抽出力 | 1回の注文で出す杯数。すべての報酬の土台なので序盤ほど伸びが大きい |
| イベント | 章をすべてクリアしたときのまとめ報酬だけ |
| クイズ接客 | 確認クイズに**1度目の回答で**正解したときのチップだけ |
| 常連サービス | **その日いちばん最初に★を取った1問だけ**。倍率は連続学習日数ぶん積み上がる |
| 自動営業 | 画面を表示している間の自動売上の速度 |

常連サービスは「今日の1杯目」に集中して乗るため、毎日開くほど得になります。連続日数は7日分が
上限（皆勤の日めくりで10日に広がり、途切れても3日分から再開）です。

6つ目の「自動営業」は、アプリ画面を表示している間だけ少しずつ売上を作ります。こちらも
★の条件はなく価格だけが歯止めで、速度は現在の「問題を1問初クリアした売上」の毎分0.5〜5%です。
画面を閉じている間やオフライン中の売上はなく、次の★を取るまでに受け取れる額は最大5問分です。
最上位設備でも上限まで100分かかるため、問題を解くことが報酬の中心である点は変わりません。

#### 序盤の解放ペース

★の条件がないぶん、**序盤にできることが増える速さはRank1の価格がそのまま決めます**。
問題の初回クリアは500コイン（店構えLv1の1杯 × 500）から始まり、1節はおおむね2問なので、
最も安いRank1（🫙 小さなチップ瓶 1,800コイン）が**1〜2節クリアでちょうど1つ買える**額です。

| 進み具合 | 持っている設備 |
|---|---|
| ★2（1節クリア） | 0個 — まだ買えない |
| ★6（3節クリア） | 1個 |
| ★9（1章クリア） | 3個 |
| ★22（2章クリア） | 6個（6系統のRank1が揃う） |
| ★50（4章クリア） | 12個 |

以前はRank1が300〜2,500コインだったため、数問解いた時点で6系統すべてのRank1が同時に買え、
1章を終える前に店が一気に完成していました。Rank1〜5だけを引き上げ（Rank1は約6倍、
Rank5は約1.27倍）、Rank6以降と出店費は据え置いてあります。序盤の数万コインは完走時の
生涯売上（26兆）に対して無視できる大きさなので、**投資率は 41.21%→41.23% とほぼ動きません**。
このペースは `tools/simulate-cafe.sh` が上下両側から検査します（緩めすぎ・絞りすぎの両方で落ちます）。

設備に加えて、コインを投資して店舗ネットワークを繰り返し拡大できます。出店上限は★4〜502で
段階的に広がります。各店舗の注文数と、完成した章の問題数に応じて育つブランド倍率が設備効果へ
掛かるため、学習に合わせて報酬の桁も少しずつ大きくなります。章制覇ボーナスは、その章の問題数に
比例した通常報酬の25%が基準です。

ブランド倍率は**復習でも育ちます**。復習で正解した問題1問につき1回だけ加算し、初回クリア1問より
小さい重みにしてあるので、新しい問題を解くより復習した方が儲かることはありません。倍率は
これからの報酬に掛かるため、**早く復習した方が得**です。加えて、復習で正解すると自動売上の枠が
戻ります。全680★を取り終えると★が増えなくなり、それまでは★のたびに戻っていた枠が尽きてしまうため、
完走後は復習が自動営業設備を動かし続ける入口になります。復習でコインを直接もらうことはありません
（クリア済みの問題は何度でも解き直せるので、支払うと無限に稼げてしまう）。

★520以降は、収益倍率に影響しない**終盤改装プロジェクト**へ任意で投資できます。
20問分の★を追加で獲得するたびに次の段階が自動で解放され、現行教材（680★）では
★520から680までの20刻みで9段階あります。今後章を追加しても、新しいコインの使い道が
同じ間隔で増えます。価格は基準2,000億から**1段ごとに1.5倍**です。

さらに、設備とは別枠の**スペシャルアイテムが全12種**あります。未発見の枠や総数は表示されず、
新しく見つかったときだけカフェとアイテムタブに通知マークが付きます。
**同じアイテムは1つしか持てません**（購入済みのものは買えません）。

**1枚のカードが持つ効果は1つだけ**です。効果を束ねると、そのカードが何のカードなのか
言えなくなります（「一発で解いた」と「5回以上粘った」のように条件が正反対のものまで
同居していました）。12枠に収まるところまで効果を削り、残したものは全て単独カードにしています。

| アイテム | 効果 | 解放 |
|---|---|---|
| 🪙 ラッキーコイン | 5%の確率で大当たり（獲得コイン+100%） | 問題・復習問題への正解ごとに1%抽選 |
| 🗒️ コンボスタンプ帳 | 5問クリアするたび、その問題のコインが7倍 | 同じ日に異なる15問 |
| 🥄 一発仕上げのタンパー | ヒントなし・1回の提出でクリアした問題が+20% | 1章をヒントなしで制覇 |
| 💧 粘りのドリッパー | 5回以上提出してクリアした問題が2倍 | 1問へ累計10回提出 |
| 📅 皆勤の日めくり | 「今日の1杯目」の連続日数の上限が7日→10日 | 7日連続で学習 |
| 🚚 移動販売トラック | 注文の集客が2店舗ぶん増える | 店舗を5店まで広げる |
| 📣 ひらめきメガホン | 確認クイズを1度目の回答で正解したときのチップが20倍 | 1度目の回答で20問連続正解 |
| 🎂 祝福のホールケーキ | 章の初制覇コインが4.5倍 | 1章を同じ日に制覇 |
| 🗺️ フランチャイズ地図 | 新店舗の出店費が25%OFF | ★170 + 累計5000万 |
| 🧰 マイスター工具箱 | 設備アップグレードが20%OFF | ★240 + 累計5億 |
| 📖 **復習ノート** | 復習が育てるブランド倍率の成長が4倍 | **復習で異なる200問**（重い） |
| 🏆 **生涯学習トロフィー** | すべての学習報酬が13%増加 | **無傷で25問連続クリア**（重い） |

ラッキーコインの価格は、幸運の数字を並べた**77,777コイン**です。

下2つが**取得の重いアイテム**です。必須664問の3分の1以上を復習するか、ヒントなし・1回の提出で
25問続けないと姿を見せません。残り10個は学習を進めれば自然に手に入ります。

解放のされ方は2通りで、10種は**特別な達成条件または正解時の抽選**（★の数ではなく学ぶ過程そのもの）、2種は
**学習の節目**（★の数と累計コイン）です。手に入れたカードには達成条件が表示されます。
いちど達成すれば、あとで連続が途切れても解放は取り消されません。

ラッキーコインだけは、初回問題・復習問題を問わず、全ケースへ正解するたびに1回、1%の確率で抽選します。
不正解では抽選せず、外れた抽選を再起動で引き直すこともできません。

初回の条件を逃しても取り返せます。同じ日に異なる15問を復習する、章の全問へもう一度正解する、
復習で異なる25問に連続正解する、といった復習でも対応するアイテムが解放されます。
ラッキーコインの抽選を除き、同じ1問・クイズの連打では数は増えず、復習では★や
通常の学習報酬も再付与しません。

**確認クイズだけは取り返せません。** ひらめきメガホン（📣）が数えるのは
**1度目の回答での連続正解**だけで、答え直しは数えません。不正解のフィードバックは正解の記号を
出すので、答え直しを数えると「読んで押すだけ」で解放できてしまいます。
チップも同じ理由で1度目の回答だけです。
また、カフェを育てず全問を終えた場合は、★条件を満たしている節目型アイテムの未所持分を完走記念品として
自動で受け取ります。新しい章や節目型アイテムが追加された場合も、その時点の全章を終えれば再評価されます。

#### 店構えの絵

画面の左に出る店構えは、`web/cafe-scene.js` が1枚のSVGとして描いています（外部ライブラリなし）。
店舗ランク1〜12で建物の骨格と時代の配色が変わり、購入した設備がそのまま絵の中の要素として増えます。
ランク1は屋台、ランク7で建物が完成し、ランク8以降はその建物のまま夜へ向かって配色と演出が変わります。
朝の光から星空まで、進み具合が一目で分かるようにしてあります。

## 必要なもの

学習アプリ本体は **JDK 21以降** で動きます。JDK 21を使う場合は21.0.12以降の
security updateを推奨します。Mavenもnpmも不要です。
`labs/testing-maven` と `labs/frameworks` は、実際の依存管理、JUnit、各runtimeを学ぶため
Maven 3.9以降を別途使います。

```bash
javac -version    # 21以上で起動可能。21なら21.0.12以上を推奨
```

入っていない場合は `brew install openjdk@21` などで入れ、最新のsecurity updateまで
更新してください。起動時は2026年7月CPUのbaseline（21.0.12 / 25.0.4 / 26.0.2）を確認し、
古ければ警告しますが起動は続けます。
JRE ではなく **JDK** が必要です（あなたのコードをコンパイルするため）。

## 起動する

```bash
./run.sh
```

ビルドしてサーバを起動し、ブラウザが自動で開きます（http://localhost:8123）。
終了は `Ctrl+C` です。

| オプション | 意味 |
|---|---|
| `./run.sh --port 9000` | ポートを変える（埋まっていたら+1して探し、実際に使ったポートを表示します） |
| `./run.sh --no-open` | ブラウザを自動で開かない |
| `JQ_JAVA_HOME=/path/to/jdk ./run.sh` | 使うJDKを指定する（複数入れている場合） |

> JDKが複数入っている環境（Homebrew / sdkman / IDE付属など）でも動くように、
> `javac` と `java` は必ず同じJDKから使い、出力は JDK 21 でも動く形にしています。
> JDKを切り替えたときは自動でビルドし直します。

### アイコンをクリックして起動する（macOS）

毎回ターミナルを開くのが面倒なら、Dock から1クリックで起動できるアプリを作れます。

```bash
tools/make-app.sh
```

`~/Applications/Java Café.app` ができます。**Dock にドラッグ**すれば、以降はアイコンを
クリックするだけでブラウザが開きます（Spotlight で「Java Café」でも起動できます）。

**止めるときは、Dock アイコンを右クリック →「終了」**（⌘Q でも同じ）。普通のアプリと同じで、
遊んでいる間だけ Dock に残り、終了するとサーバも一緒に止まります。ログアウトや再起動でも
きちんと止まります。

- ターミナルを開いたままにしなくていいです（サーバはアプリの裏で動きます）
- すでに動いているときは二重に起動せず、ブラウザを開くだけです
- ターミナルが無いので、ビルドの失敗やポートの取り合いは**ダイアログ**で知らせます
- ログは `build/server.log` に出ます

ターミナルから起動・停止したいときは、アプリが呼んでいるスクリプトを直接使えます。

```bash
tools/launch.sh            # 起動（バックグラウンド）
tools/launch.sh --stop     # 止める
tools/launch.sh --status   # 動いているか調べる
```

| オプション | 意味 |
|---|---|
| `tools/make-app.sh --dest /Applications` | アプリを置く場所を変える |
| `tools/make-app.sh --name "Java道場"` | アプリの名前を変える |
| `tools/make-app.sh --jdk /path/to/jdk` | アプリが使うJDKを指定する |
| `JQ_PORT=9000 tools/launch.sh` | ポートを変える |

> アプリは `tools/launch.sh` を呼ぶだけの薄い入れ物です（AppleScript の stay-open
> アプレット。こうしておくと「終了」の Apple Event を受け取れるので、右クリック →「終了」で
> サーバまで止められます）。レッスンやコードを直したあとに作り直す必要はありません
> （起動のたびに必要なところだけビルドします）。作り直しが必要なのは
> **このフォルダを別の場所に移したとき**だけです。
>
> Finder から起動されたアプリは Homebrew や sdkman のJDKを見つけられない（`PATH` が
> `/usr/bin:/bin` などに限られる）ので、`tools/make-app.sh` を実行した時点のJDKの場所を
> アプリに書き込んでいます。そのJDKを消したときは、`tools/make-app.sh` で作り直してください。
>
> アプリで起動したまま `./run.sh` すると、ポートが埋まっているので別のポートに立ってしまいます。
> ターミナルから起動し直すときは、先にアプリを終了する（または `tools/launch.sh --stop`）
> ようにしてください。

## 使い方

1. 学習ホームで **▶ 続ける** を押す（または章カードを開いて好きなレッスンを選ぶ）
2. 解説を読み、**サンプルを実行**して動きを目で確かめる
3. エディタに自分でコードを書く
4. **▶ 実行して採点** … 実行するとそのまま全テストケースで採点します。全部通ると ★ が付き、
   通らなければどのケースで落ちたかが出ます。**実行と回答は同じ操作**です
5. 次の問題へ進む。章末演習では、続けて「組み合わせ」「実践」に挑戦する
6. 一度クリアした問題は **🔁 復習する** から解き直せる（→ [復習モード](#復習モード)）

ボタンを「試す」と「提出」に分けていないのは、**考えながら書ける**ようにするためです。
分かれていると「まだ提出できる形になっていないから試すだけ」と身構えてしまいます。
1つにすると、書けたところまでを気軽に走らせて、落ちたケースを見ながら直していけます。
そのぶん失敗の回数は増えるので、復習の苦手度は1回あたり0.25点しか上がりません
（→ [復習モード](#復習モード)）。

**▶ 続ける** は、前回いた問題がまだ未クリアならそこへ戻り、クリア済みなら次の問題
（同じレッスンの2問目 → 次のレッスンの1問目、の順）へ進めます。

クリアしたレッスンには **★** が付いて文字がはっきりした色になり、まだのレッスンは
**○** と薄い色になります。★ が付くのは **そのレッスンの全問** をクリアしたときで、途中は
「学習中」と出ます。メニューでもサイドバーでも、総量を意識せず現在地だけ確認できます。

| ショートカット | 動作 |
|---|---|
| `⌘/Ctrl + Enter` | 実行して採点 |
| `Tab` | 選んでいる補完候補を入れる（候補が出ていなければインデント） |
| `Shift + Tab` | インデントを戻す |
| `↑` `↓` | 補完候補を選ぶ |
| `Esc` | 補完候補を閉じる |
| `Ctrl + Space` | 補完候補を自分から出す |

書いたコードは自動保存されるので、ブラウザを閉じても続きから再開できます。

### 復習モード

学習ホームの **▶ 続ける** の下にある **🔁 復習する** から、一度クリアした問題を解き直せます。

```
┌──────────────────────────────────────────────┐
│   ╭───╮   🔁 復習する                        │
│   │⏰ 3│   解き直して定着させる               │
│   ╰───╯   忘却曲線でそろそろ確認したい問題から │
│           ┌────────┬────────┬──────────────┐ │
│           │🔁すべて│🔥苦手  │🔖ブックマーク│ │
│           │  7問   │  3問   │     2問      │ │
│           └────────┴────────┴──────────────┘ │
│           今回の出題    [ ▶ 復習を始める ]    │
│           ⏰ 期限切れ 3問 ＋ 早めの復習 7問   │
├──────────────────────────────────────────────┤
│  1問だけ選んで復習する                       │
│  2-1 変数を作って使う ⏰19日過ぎ 🔥苦手 [▮] │
│  5-2 while文で繰り返す ⏰7日過ぎ もう一度[▯] │
│  1-1 はじめての出力     あと5日   安定  [▯] │
├──────────────────────────────────────────────┤
│  🔖 ブックマークしたクイズ（押すと見に行く） │
│  1-3 Q2 コメントは何のため？   未回答   [▮]  │
│  5-2 Q1 breakを書き忘れると？  ❌不正解 [▮]  │
└──────────────────────────────────────────────┘
```

出題は**忘却曲線の期限順**です。問題ごとに「次に確認したい日」を持ち、期限を過ぎたものから
順に出します。抽選ではないので、そろそろ危ない問題が後回しになりません。

- **一度正解するとしばらく出てきません。** 正解するたびに間隔が伸びます
  （**1 → 3 → 7 → 14 → 30 → 60 → 120日**）。初クリアの翌日が最初の期限です。
- **同じ日に失敗してから通した問題は、間隔を1段戻します。** 危なかったので早めにまた出ます。
- **失敗しただけでは期限は動きません。** 通せていないのだから、また出てくるのが正しい挙動です。
  そのまま閉じても期限切れとして残り、次の復習で出てきます。
- 期限日そのものは保存せず、「最後に復習した日 + レベルの間隔」で毎回引き直します。
  だから間隔（`REVIEW_INTERVAL_DAYS`）を調整すると、過去の記録にもそのまま効きます。

苦手度は**同じ期限のときにどちらを先に出すか**を決めます（出題そのものは期限が決めます）。

- 実行が通らないと苦手度が **0.25点** 上がります（上限8点）。実行＝採点なので書いている
  途中の失敗も全部届くため、1回あたりを従来の1/4にしてあります。4回失敗して1点ぶんです。
- **復習で正解すると1点まとめて下がります。**
  一覧には `🔥 よく間違えた` / `🔥 苦手` / `もう一度` / `安定` と出ます。
- **ブックマーク**は、しおりのボタン（塗り＝付いている / 線だけ＝付いていない）で
  問題の見出しからも復習の一覧からも付け外しできます。期限が同じときに先に出るようになり、
  「ブックマーク」で絞り込めば付けた問題だけを復習できます。
- **確認クイズにも同じしおりを付けられます**（問いの右にボタンがあります）。ただしクイズは
  **出題されません**（解き直す提出物が無く、期限も苦手度も持ちません）。復習ホームの
  「🔖 ブックマークしたクイズ」に並び、押すとそのクイズまで移動します（着いた問いが一瞬光ります）。
  答える前のクイズにも付けられ、一覧には `未回答` / `✅ 正解` / `❌ 不正解` が出ます。
  **★もコインも苦手度も動きません。**
  進捗では別の集合（`progress.json` の `quizBookmarks`）で持ちます。問題キー（`5-2#1`）と
  クイズキー（`5-2#1` ＝ 2問目）は同じ形なので、同じ集合に入れると取り違えます。
- 1回の復習は最大10問です。**期限が来たものを先に出し、10問に足りなければ期限が近い順で
  補います**（「早めの復習」と表示）。0問の画面を見せると復習の習慣が途切れるので、
  いつでも始められる形にしています。終わると正解数が出ます。

復習では**ひな形から解き直します**。前に書いた解答は消えません（復習中は保存しないので、
通常のレッスン画面を開けば以前のコードがそのまま残っています）。ヒントと模範解答は
クリア済みなのでいつでも見られます。

★は増えないので、コインも増えません。ただし**達成型アイテムの解放条件は復習でも進みます**
（「復習で異なる10問に連続正解」など。→ [カフェ画面](#カフェ画面)）。

### コードを書く欄の補助

`Tab` で4スペース入り、`Shift+Tab` で戻ります。`Enter` は前の行のインデントを引き継ぎ、
`{` の後ろなら1段深くします。

`(` `{` `[` `"` は自動で閉じ、カーソルは間に残ります（`"` を打つと `"|"` の状態になります）。
**自動で入った閉じ記号の前で自分でも閉じ記号を打つと、重複させずに通り抜けます**
（`println(` `"` と打って `Hello` `"` `)` と打つと `println("Hello")` になります）。
通り抜けるのはこの場合だけで、**ひな形にあった閉じ記号や自分で書いた閉じ記号の前では、
打った文字がそのまま入ります** ― 打ったのに何も入らない、という状態を作らないためです。

`"` を足さない場面が3つあります。**文字列やテキストブロック（`"""`）の中**、**`"""` を
打っている途中**（`""""` になってしまうため）、**直後が英数字のとき**（既存の語を壊さないため）です。
`'`（`char` の引用符）は自動で閉じません ― コメントに `don't` と書いたときに勝手に増えるほうが
煩わしいためです。

`Backspace` は、`()` や `""` のように空のペアならまとめて消し、行頭のインデントは4つまとめて消します。

### コード補完

クラス名・メソッド名・変数名・パッケージ名を途中まで打つと、候補が出ます。
`sc.` のように `.` を打った直後は、その変数の型に合わせたメソッドだけが並びます
（`List<String>` なら `list.get(0).` で String のメソッドが出る、というところまで追います）。
自分で書いたクラス・メソッド・変数も候補になります。

候補は `↑` `↓` で選び、`Tab` で入ります。**macOSでは `Ctrl+P` / `Ctrl+N` でも選べます**
（Emacsキーバインド）。この割り当てが働くのは候補が出ているあいだだけなので、出ていないときの
`Ctrl+P` / `Ctrl+N` は、macOS本来の「1行上へ／下へ」のままです。

メソッドなら `()` まで付き、引数があるものはかっこの中にカーソルが入ります。
**候補が出ていないときの `Tab` は、今までどおりインデント**です。

文字列やコメントの中では出ません。日本語入力の変換中も邪魔をしません。

### 詰まったとき

**💡 ヒント** を押すと1つずつ開きます。全部開くと **📖 模範解答** が見られるようになります。
ヒントを使ってもクリア扱いになるので、遠慮なく使ってください。
ただし模範解答は写して終わりにせず、**1行ずつ「なぜそう書くのか」を自分の言葉で説明できるか**
試してみるのがおすすめです。

**文書の採点は「文章の巧みさ」ではなく「事実の位置」を見ます。** `## 見出し`で本文を切り分けてから、
時刻とエラー名が「検知」に、`queries=`の値と配備の版が「確認」に、戻す先の版が「切り戻し」にあるかを

数と単位を持つこと、ADRの却下した案が箇条書きで2件以上ありそれぞれに分量があることを見ます。
これは「全節を空にして事実を1箇所へ並べる」「案の名前だけ書く」を弾くためです。

測れないものは測りません。文章の巧拙、論理の妥当性、書かれた理由が本当に妥当かは採点対象外です。
却下理由の有無は分量による代理指標なので、長く書けば通ります。理由の中身を「ため・から・ので」の
ような接続表現で測る案は採りませんでした ― これらの語を使わずに理由を書いた良い文章を落とすためです。

加えて、各章に **4択の確認クイズ** が入っています（全522問）。
出力の一致では試せない次のような論点は、こちらで出題しています。

**クイズを足す基準は「出力の一致では試せない論点か」です。密度ではありません。**
基礎編は章あたり4〜6問で、後半の章より少なく見えます。しかし `⚠️ 間違えやすい点` を全部並べて
既存クイズと突き合わせると、大半（`break` の書き忘れ、既定コンストラクタの消滅、パッケージを跨いだ
`protected`、`remove(int)` と `remove(Object)`、`substring` の境界、`while (...);` の空文だけのループなど）は
すでに出題済みでした。2026-08-17の点検で**まだどこにも無かった6問だけ**を足しています
（`7-5` 参照の再代入、`8-5` 1ファイル2つの `public`、`11-4` 継承関係の無い `instanceof`、
`13-5` 親子のマルチキャッチ、`16-5` `length` / `length()` / `size()` と拡張for中の `remove`）。
**レッスン数に対する比で判断すると、すでに測っている論点をもう一度出すことになります。**

> 本教材は資格取得ではなく、Javaで安全に設計・実装・テスト・運用できるようになることを目的にしています。
> 解説では、実装時に間違えやすい形を `⚠️ 間違えやすい点` として `✅` / `❌` の対比で載せています。
>
> クイズの正解と解説は、答え合わせをするまでブラウザへ送られません（判定はサーバ側で行います）。
> 何度でも答え直せます。ただし**チップ（コイン）が出るのは1度目の回答で正解したときだけ**です
> ― 不正解のあとは正解の記号が画面に出るので、答え直しにも払うと「読んで押すだけ」で
> コインが増えてしまいます。正解数と★の判定は最後に選んだ答えで数えるので、
> 答え直して覚え直すことは今までどおり歓迎されます。

> 第1章・第2章と `3-1` は入力を受け取らない問題なので、出力が1通りに決まります。

#### 求める文言は問題文へ書く

学習者が提出前に読めるのは **問題文・ひな形・表示ケース** だけです。隠しケースの中身は見えません。
だから、隠しケースだけが完全一致で求める固定文言があると、**正しく実装しても必ず落ちます**。

2026-08-16のレビューで、この形が10問ありました。

    23-4    「別roleは403です」としか書いておらず、隠しケースが `! 権限がありません` を求めていた
    28-4#1  不正入力の分岐そのものを書いておらず、隠しケースが `400 Bad Request` を求めていた
    29-5    表示ケースは `name: nameは必須です` だけで、他2つの検証メッセージが隠しケースにしか無かった

**ヒントに書くのは解決になりません。** ヒントを開くと報酬が減るので、必須の情報をそこへ置くと
「読まないと解けないが、読むと損をする」状態になります。文言は問題文へ書いてください。
文言そのものを考えさせたいなら、出力の比較対象から外します（`sourceChecks` は文言を検査できません）。

**ケースの `label` は場面を書きます。** ラベルは落ちたケースを知らせるときにそのまま出るので、
`隠しケース1` のような番号だけでは何が起きたか伝わりません（`60-2` `60-3` `61-3` `62-3` の20件が
この形でした）。「名前が空白だけ」「上限ちょうど」のように、その場面を書いてください。

どちらも `./tools/check-case-fairness.sh` が全件まとめて検査します（1秒）。

#### sourceChecks は「その構文が到達目標のとき」だけ書く

`sourceChecks` は挙動をテストケースで固定できない場合の補助です。次の線引きで使います。
**到達目標は推測しなくてよくなりました。** その章の `objectives` と、そのレッスンの
`objectiveIds` が指す目標文が判断の基準です（「到達目標を書く」）。目標が
「`switch` で値ごとに分岐を書ける」なら `switch` を縛ってよく、
「在庫が負にならないようにできる」なら字面ではなく隠しケースで確かめます。

| 書いてよい | 書かない |
|---|---|
| `if` / `for` / `switch` / `sealed` / `@Entity` / `@WebServlet` のように、**その構文やannotation自体を習う**レッスン | データ構造の指定（`LinkedHashSet`、`new TreeMap`、`Map.of`） |
| 到達目標がAPIの使用そのものであるとき（`Files.exists`、`prepareStatement`、`@NotBlank`） | 変数名やメソッド名の指定（`List<String> missing`、`static String resolve`） |
| | 制御構文の指定（`switch` で書けと言うが `if` でも等価なとき） |

書かない側は、正しい別実装を不正解にしてしまいます。

**別解を弾いていると分かったら、消す前に緩められないかを見ます。** 学習の意図は正しくて、
書き方の1つだけを許してしまっているなら、選択肢を足せば意図を保てます。

| 直す前 | 直したあと | 弾いていた別解 |
|---|---|---|
| `x\s*\*\s*2` | `x\s*\*\s*2|2\s*\*\s*x` | `x -> 2 * x` |
| `\bfor\s*\(` | `\bfor\s*\(|\bwhile\s*\(` | `while` で回す |
| `isEmpty\s*\(` | `isEmpty|size()==0|count()==0` | `size() == 0` |
| `getSession\s*\(\s*\)` | `getSession\(\s*(?:true\s*)?\)` | `getSession(true)`（引数なしと同じ動き） |

消すのは、**出力だけで正しさが決まる**とき（別解を許しても検査が何も足していないとき）です。

`./tools/classify-source-checks.sh` が全件を4つへ振り分けます。**A 学習対象**（到達目標か問題文で
名指ししている）、**B 足場の見張り**（ひな形が満たす。これは正常）、**C 要判断**（AでもBでもない）、
**D 禁止系**（`minimum=0`）。Cへ落ちたものを読んで、緩めるか消すかを決めます。
Aの判定は語の一致なので、問題文の言い回しが検査の字面と違うとCへ落ちます（「複合代入の形で」と
書いてあり `*=` とは書いていない、など）。**Cは「消すべき」ではなく「読んで決める」**の意味です。

**章の主題がJavaの書き方でないなら、字面は縛りません。** framework・選定・運用・データ・
セキュリティ・JVM・性能・可観測性の章（第30・37・38・45〜48・50〜56・60〜63章）からは、
この基準で**合わせて131件**を削除しました。
これらの章の到達目標は製品やツールを扱う力なので、挙動は隠しケースで固定し、domainの結果は
`artifact`・`project`・`runtime-lab`の受け入れ条件で見ます。

削除の判断は3つの条件で行いました。**①その構文やAPI自体がそのレッスンの到達目標か**、
**②隠しケースが挙動を固定していて、構文の指定が検査に何も足していないか**、
**③期待出力が「正しい実装」と「何もしない実装」を区別できるか**です。
①に当たるものは同じ章の中でも残しています。

③を見落とすと穴が開きます。`ch45`の `45-7` は `MiniJUnit` でテストを走らせ、出力の
`PASS / Failures: 0` を期待値と比べます。**空のテストメソッドは何も検証しないまま成功する**ので、
中身が空のひな形でも期待出力と一致してしまいます。テスト自体を書かせる問題では、
隠しケースは挙動を固定できません。この種の問題では `sourceChecks` が採点の本体なので外せません
（`45-7` では `assertEquals` を2回以上要求しています）。

**`sourceChecks` を外したら `--strict-starters` を必ず通してください。** ③の見落としは
「ひな形が最初から合格している」として出ます。

| 残した例 | 残した理由 |
|---|---|
| `ch45`の`@Test`・`assertThrows`・`@ParameterizedTest`・`@BeforeEach` | JUnitのannotationそのものが到達目標 |
| `ch45`の`Clock.fixed`と`Instant.now`の禁止 | 「時刻を差し替えられるように書く」がテスト設計の到達目標 |
| `ch55`の`Locale.ROOT` | 既定ロケールで出力が変わると採点が環境依存になる。隠しケースでは検出できない |
| `ch57`の`Files.*`・`StandardCharsets`・`ATOMIC_MOVE` | 標準APIの使い方そのものが章の主題 |
| `ch63`の`Duration.between`・`isAfter` | 「時刻を文字列で比べない」がレッスンの主題 |
| `ch30`の`getSuperclass`・`LinkedHashMap`のaccess-order・`try (` | **出力では区別できない。** 入力3通りに固定出力を返す問題は`switch`で直書きしても通り、自前の構造でLRUを作っても、`finally`で手で閉じても出力は同じ |

#### ③に当たる本課題へ、あとから足した分

③（期待出力が「正しい実装」と「何もしない実装」を区別できるか）は、**削除の見落とし**だけでなく
**最初から無かった穴**としても出ます。2026-08-17の点検で、課題文がバッククォートで名指しした仕組みを
1度も書かずに通る本課題が11問見つかり、検査を24件足しました。同じレッスンの追加課題には同じ検査が
既にあった（`32-1#1`が`CountDownLatch`と`await`を要求しているのに、本課題の`32-1`は何も要求して
いなかった）ので、**追加課題側へそろえる**形で足しています。

| 足した問題 | 足さないと通ってしまう提出 |
|---|---|
| `32-1`（`new Thread`／`join`） | `System.out.println(workers * iterations)` |
| `32-2`（`new Thread`／`ConcurrentHashMap`／`join`） | 1スレッドで`HashMap`へ順に数える |
| `32-3`（`new Thread`／`countDown`／`await`） | forループで合計と2乗和を出す |
| `34-1`（`newFixedThreadPool`／`submit`／`try (`） | forループで`println(v * v)` |
| `34-2`（`supplyAsync`／`thenApply`） | forループで`println(v * 2 + 1)` |
| `34-4`（`submit`） | ひな形のプールを開いたまま、ループで直接計算する |
| `24-1`・`24-2`・`24-4`（`prepareStatement`／`setInt`／`executeQuery`／`executeUpdate`／`try (`） | 表の中身をコード側の`Map`に持って答える |
| `13-5`（`try (`） | `try`・`finally`で手で`close()`を呼ぶ（出力は同じ） |
| `14-4`（`append`／`reverse`） | `String`の`+`でつなぎ、逆順を自分で組み立てる |

「スレッドを作る」のような要求は、正しい別解を弾かないように書きます（`\bnew\s+Thread\s*\(` だけでは
`Thread.ofPlatform()` を弾くので、`|Thread\s*\.\s*of(Platform|Virtual)\s*\(` を足してあります）。

### 概念レッスンを書く

**提出課題を付けると測る対象がずれてしまう論点**だけを、解説と確認クイズで扱うレッスンです。
`lessonType` を `concept` にすると、`task` と `extraTasks` を書けなくなり、**クイズ全問正解で★が1つ**付きます。
★は章クリアの条件にもカフェ報酬にも入ります（進捗キーは `70-1#q`。`Lesson.CONCEPT_TASK_ID`）。

```json
{
  "id": "70-2",
  "lessonType": "concept",
  "title": "V字モデル：どの試験が何を確かめるか",
  "objectiveIds": ["ch70-o2"],
  "explanation": "## 試験は「動くか」ではなく「決めたとおりか」を見る\n\n…",
  "quiz": [
    { "question": "受入試験が確かめる相手はどれでしょう。", "choices": ["…"], "answer": 2, "explanation": "…" }
  ]
}
```

**使ってよい場合の線引きはひとつだけです。** 提出課題にすると、測るものが学習内容から別のものへ
変わってしまうかどうかです。

| 概念レッスンにする | 通常レッスンにする |
|---|---|
| 工程名と成果物の対応、V字モデルの対応、工程型と反復型の選び分け、保守の区分のように、**判断と用語**が中身 | 集計・突き合わせ・変換のように、**作業**として書ける中身（WBSの100%ルール検査、3点見積り、稼働率から年間停止時間、トレーサビリティの欠落検出） |
| コードにすると `Map` を引く練習になる | コードにすると論点そのものを測れる |
| 文書で提出させると、当てられない文言を正規表現で求めることになる（「求める文言は問題文へ書く」） | 出力やartifactの検査で正しさが決まる |

**クイズは3問以上必要です**（`ContentLoader` が止めます）。★の根拠がクイズだけなので、
少ないと当て推量で★が付きます。あわせて `./tools/check-quiz-fairness.sh` を必ず通してください。
正解だけが具体的で長い状態は、この形のレッスンでは★がそのまま取れてしまいます。

到達目標は、そのレッスンのクイズが測ります。`check-objective-terms.sh` も概念レッスンでは
**クイズの本文**から名指しした語を探すので、目標で `…` で囲んだ語はクイズに出してください。

**復習の対象にはなりません。** 解き直す提出物が無いためです。`reviewedTaskPercent` の分母からも
概念レッスンの★を外してあります（外さないと復習を全部終えても100%へ届きません）。

**提出課題を持っていたレッスンを概念レッスンへ変えるときは、★のキーを読み替えます。** ★は
`50-4#1` から `50-4#q` へ変わるので、そのままではすでにクリアした人の★が消え、章クリアも外れます。
`ProgressStore.CONCEPT_MIGRATED_TASK_KEYS` に旧キーを足すと、読み込みのときだけ `#q` へ読み替えます
（書いたコードやヒントの開示数は持ち込みません。もう存在しない問題のものです）。

**概念レッスンを足したら、必ずどちらかの一覧へ書きます。** 提出課題を持っていたなら
`ProgressStore.CONCEPT_MIGRATED_TASK_KEYS` へ旧キー（`53-5#1`）、最初から概念レッスンとして書いたなら
`LayerCompletionCheck.NEW_CONCEPT_LESSON_IDS` へレッスンIDです。`./tools/check-layer-completion.sh` が
**教材側の概念レッスンを起点に、どちらにも入っていないものを落とします**。検査が自前の写しを持っていた
あいだは、読み替えの足し忘れ（`53-5`）を検査も同じように見落としていました。読み替えの一覧は
`ProgressStore.conceptMigratedTaskKeys()` から読みます。

**元からあるクイズの順番は動かせません。** `progress.json` の `quizChoices`（選んだ選択肢）と
`quizBookmarks`（しおり）はどちらもクイズの**番号**で保存しているので、並べ替えると
過去の解答が別の問いの解答として扱われ、しおりも別の問いへ移ります。クイズを足すときは
**既存の問いを先頭に残したまま、後ろへ足します**（新しく作った章のクイズなら、まだ誰も解いていないので
正解の位置を散らせます）。

### 表を写すだけの問題を見つける

2026-08-17の棚卸しで、**問題文の対応表を写して引くだけ**の問題が8件見つかりました。判断の基準は
「コードが表の転記以外に何かしているか」です。

| 直した形 | 対象 |
|---|---|
| 概念レッスンへ変換（提出課題を外す） | `50-4`（接頭辞で役割を分類）・`53-3`（3つの0/1から3値）・`53-4`・`53-5`（要件からIDへ引く） |
| 問題を差し替え（進捗キーは変えない） | `50-2#1`（語を数える→環境差の突き合わせ）・`50-5#2`（用語6分類→1つのclass fileと複数のJVM）・`51-5#3`（2つの表を引く→非推奨APIを重い順に並べる）・`53-6#3`（3製品の表を写す→移行できない機能の洗い出し） |

**紛らわしいが直さなかった例**も残しておきます。`51-2#1`（compile / target / runtime の大小）、
`53-1#1`（多基準の絞り込み）、`62-5#1`（優先順位付きの判定）、`54-5#2`（段階ごとに許される操作）は、
表が**規則**として与えられていて、コードは集合演算・優先順位・突き合わせをしています。
問題文に表が出てくること自体は、隠しケースだけが文言を求めないための**必要な配慮**です
（「求める文言は問題文へ書く」）。表の有無ではなく、**コードが表の転記だけで終わっていないか**で見ます。

**章に1問もコード問題が無い状態は避けてください。** 3層のうちコード層が0件になり、
その章では「書けるようになったか」を何も測っていないことになります。システム開発ライフサイクル編の
6章は、どの章にも計算か突き合わせのコード問題を2問以上置いてあります。
検査は `./tools/check-layer-completion.sh` です。

### 事前確認レッスンを書く

Maven、Gradle、Docker、開発用ポートなど、教材本題とは別の環境条件を最初に実測するレッスンです。
レッスンの `lessonType` を `preflight` にし、通常の `task`、`samples`、`quiz` は置きません。事前確認は
★、問題数、章クリア条件、カフェ報酬に含まれません。

```json
{
  "id": "60-0",
  "lessonType": "preflight",
  "title": "事前確認：Spring Boot labを起動する準備",
  "explanation": "必要な理由、確認コマンド、初回取得について説明します。",
  "preflight": {
    "buttonLabel": "Spring Bootの準備を確認する",
    "checks": [
      {
        "id": "maven",
        "type": "tool",
        "tool": "maven",
        "label": "Apache Maven",
        "minimumVersion": "3.9",
        "help": "Mavenをインストールし、mvnをPATHへ追加してください。"
      },
      {
        "id": "http-port",
        "type": "port",
        "port": 8080,
        "label": "HTTPポート",
        "help": "8080番を使うプロセスを停止するか、labの設定を変更してください。"
      }
    ]
  }
}
```

`tool` は任意コマンドではなく、`java` / `javac` / `jcmd` / `jfr` / `maven` / `gradle` / `docker` の
固定検査だけを指定できます。**`jfr` は在るかどうかでは判定しません。** OpenJ9系の配布物は
`jfr` コマンドを同梱していてもJVM側が記録を作れないので、短い記録を実際に作って確かめます
（`JdkCapability.canRecordFlight`）。同じ判定を `RuntimeLabRunner` も呼ぶので、**事前確認は通るのに
labだけ環境不足になる、という食い違いが起きません**。`jcmd` と `jfr` は版を表示しないので、
`minimumVersion` は書けません（書くと `ContentLoader` が止めます）。`port` はlocalhostへ一時的にbindできるかを調べます。`required: false` にした項目は
失敗しても準備完了を妨げません。例えばQuarkusのJVM演習に対するNative build用Dockerが該当します。
インストールやプロセス停止は自動実行せず、学習者自身が`help`を読んで対処してから再確認します。

環境は後から変わり得るため、結果自体は進捗や★として保存しません。必須項目がそろった時刻だけを
ブラウザへ7日間記録し、章の「始める」ボタンで事前確認を何度も強制しないようにしています。

### artifact問題を書く

XML、JSON、properties、SQL、Dockerfile、OpenAPI、CI YAMLなど、実務で扱うファイルそのものを
編集・検証する問題です。文字列をJavaで組み立てる代用問題にせず、学習目標と提出物を一致させられます。

```json
{
  "type": "artifact",
  "task": "server.xmlにREST機能とHTTPポートを設定してください。",
  "starterContent": "<server>\n    <featureManager>\n    </featureManager>\n</server>\n",
  "artifact": {
    "path": "src/main/liberty/config/server.xml",
    "format": "xml",
    "checks": [
      {
        "type": "xpath",
        "expression": "count(/server/featureManager/feature[normalize-space(.) = 'restfulWS-4.0']) = 1",
        "message": "restfulWS-4.0を1回だけ有効にする"
      }
    ]
  },
  "hints": ["featureManagerの内側にfeature要素を書きます。"],
  "solution": "<server>\n    <featureManager>\n        <feature>restfulWS-4.0</feature>\n    </featureManager>\n</server>\n"
}
```

artifact問題では `starterCode`、`visibleCases`、`hiddenCases`、`sourceChecks` の代わりに、
`starterContent` と `artifact` を使います。`path` は画面に表示する安全な相対パス、`format` は
`xml` / `json` / `properties` / `text` / `sql` / `dockerfile` / `yaml` のいずれかです。

| 検査type | 対象 | `expression` | `expected` |
|---|---|---|---|
| `xpath` | XML | booleanとして評価するXPath | 不要 |
| `jsonPointer` | JSON | `/openapi` のようなJSON Pointer | 必須（文字列・数値・真偽値・null） |
| `property` | properties | プロパティキー | 必須（文字列として比較） |
| `regex` | 全形式 | ファイル全体へ適用するJava正規表現 | 不要 |

XMLは整形式かを先に解析し、DOCTYPE・外部エンティティ・外部DTDを拒否します。JSONとpropertiesも
形式を解析してから個別条件を検査します。SQL、Dockerfile、YAMLは現時点では外部パーサーを
同梱していないため、`regex`による教材固有の条件だけを検査します。「構文全体が正しい」ことまで
保証する問題にはせず、`project` / `runtime-lab` で実ツールを動かす検証へつなげてください。

`message` は提出前の「検証すること」と不合格時の案内に表示されます。答えそのものを隠す用途にはせず、
受け入れ条件を具体的に書きます。要素の順序や字下げなど本題でない差はXPath等で許容し、正しい別解を
弾かないようにしてください。模範解答とひな形は `verify-solutions.sh` が実際に検証します。

### project問題を書く

既存の `labs/` を画面へ接続し、Java、SQL、Markdownなど複数ファイルを一つの変更として扱う問題です。
学習者が「編集」と表示されたファイルだけを変更し、テスト・要件・入力データなどの参照専用ファイルを
読みながら、lab自身の検証コマンドを通します。提出のたびにlabを一時ディレクトリへコピーするため、
元の `labs/` は変更されません。

```json
{
  "type": "project",
  "task": "既存注文アプリのキャンセル機能を完成させてください。",
  "project": {
    "name": "business-app-capstone",
    "source": "labs/business-app-capstone",
    "exclude": ["reference"],
    "command": ["./run-tests.sh"],
    "timeoutSeconds": 30,
    "verification": "受け入れ条件を確認する11テストがすべて成功する",
    "editableFiles": [
      {
        "path": "app/src/main/java/cafe/orders/OrderService.java",
        "solutionPath": "reference/src/main/java/cafe/orders/OrderService.java"
      },
      {
        "path": "app/db/migration/V2__add_order_cancellation.sql",
        "solutionPath": "reference/db/migration/V2__add_order_cancellation.sql"
      }
    ]
  },
  "hints": ["最初にrequirements.mdとテストを読みます。"]
}
```

| キー | 説明 |
|---|---|
| `source` | リポジトリの `labs/` 以下にある既存lab。絶対パスや `..` は不可 |
| `exclude` | 画面表示と一時コピーの両方から除外する相対パス。模範解答ディレクトリも指定する |
| `editableFiles` | 学習者が変更できるファイルと、サーバーだけが読む対応する模範解答 |
| `command` | `mvn`、`gradle`、またはlab内の固定script。学習者は変更できない |
| `timeoutSeconds` | 必須問題は1〜60秒、`required: false`の任意発展問題は1〜600秒。省略時は30秒 |
| `verification` | 提出前に見せる受け入れ条件。コマンドの内部実装ではなく、何を確認するかを書く |

画面のファイル一覧はフォルダの木で見せ、編集対象以外のテキストファイルも参照専用として並べます。`solutionPath` は、`exclude` の記述を
忘れても画面には公開されません。シンボリックリンクと `.git`、`target`、`build`、`.gradle`、
`.liberty` などの生成物は読み込み・コピーしません。提出できるのは定義済みの編集対象だけで、
1ファイル8万文字、合計30万文字が上限です。検証出力は6万byteで打ち切り、timeout時はプロセスを停止します。

`mvn` / `gradle` を使うproject問題は、実行環境に対応するコマンドと依存関係が必要です。server、DB、
HTTP、JFR、containerを実際に起動し、その生存期間やポートを管理する演習は `project` に詰め込まず、
次の `runtime-lab` として扱います。`labs/` 直下の分類と接続先は次のとおりです。

| 種類 | `labs/` 直下 |
|---|---|
| `project` | `business-app-capstone`、`logging-investigation`、`operations-capstone`、`testing-maven`、`frameworks`（spring-boot / quarkus） |
| `runtime-lab` | `platform`、`jdk-tools`、`modules`、`testing-maven`、`diagnostics`、`concurrency`、`resilience`、`sql`、`jdbc`、`transactions`、`jpa`、`http-client`、`jakarta-web`、`jakarta-ee11`、`security`、`security-platform`、`integration-data`、`delivery`、`frameworks`（comparison / spring-boot / open-liberty / quarkus） |

### runtime-lab問題を書く

`runtime-lab`は複数ファイルを編集したあと、server・DB・HTTP・JFR・containerなどを実際に起動し、
観測してから停止する問題です。ファイル隔離と模範解答の扱いはprojectと共通ですが、実行条件と
構造化された検査結果を追加で宣言します。

```json
{
  "type": "runtime-lab",
  "task": "ローカルserverへHTTP要求を送り、timeoutを確認してください。",
  "runtimeLab": {
    "name": "local HTTP boundary lab",
    "source": "labs/http-client",
    "exclude": ["reference"],
    "command": ["./run-runtime-lab.sh"],
    "timeoutSeconds": 15,
    "verification": "HTTP 200・404・request timeoutを区別する",
    "capabilities": ["server", "http"],
    "requiredTools": ["java", "javac"],
    "requiredImages": [],
    "checks": [
      {"id": "http-success", "label": "HTTP 200とJSONを受信する"},
      {"id": "http-timeout", "label": "遅い応答をtimeoutとして扱う"}
    ],
    "editableFiles": [
      {"path": "exercise/ApiClient.java", "solutionPath": "reference/ApiClient.java"}
    ]
  },
  "hints": ["接続timeoutとrequest timeoutを分けます。"]
}
```

`capabilities`は`server` / `db` / `http` / `jfr` / `container`、`requiredTools`は
`java` / `javac` / `jcmd` / `jfr` / `mvn` / `gradle` / `docker` / `docker-or-podman`の
固定値だけを使えます。両runtimeで同じCLI互換範囲を使える課題は`docker-or-podman`を指定します。
ランナーは接続可能で必要imageも揃ったruntimeを選び、固定scriptへ`JQ_CONTAINER_RUNTIME`として
`docker`または`podman`を渡します。container問題では`requiredImages`も宣言します。imageが無ければ
自動pullせず、両runtimeの準備コマンドを表示します。外部環境不足はコードの不正解や復習成績として記録しません。

実行scriptは編集対象にせず、必ず成功・失敗・TERM・INTでserver/containerを片付ける`trap`を持たせます。
ランナーが作る`JQ_LAB_PORT`と`JQ_LAB_RUN_ID`を使い、固定ポートや固定container名を共有しません。
各検査は次のtab区切りprotocolで1回だけ報告します。JSONから任意commandを組み立てたり、学習者が
編集できるscriptを実行したりしないでください。

```text
JQ_CHECK<TAB>PASS<TAB>http-success<TAB>HTTP 200とJSONを受信しました
JQ_CHECK<TAB>FAIL<TAB>http-timeout<TAB>request timeoutが長すぎます
```

timeout時は最初にTERMを送り、cleanupの猶予後に残った子プロセスを強制停止します。DockerなどJVMの
子プロセス外に資源を作る場合も、固定scriptのtrapで必ず削除します。Maven・container・特別なJDKツールが
必要な章には`xx-0`の事前確認を置き、必要ツールと、手動でpullするimageや初回download量を先に
説明してください（`java`と`javac`だけで動くlabには置きません。第30・37・47章と同じ扱いです）。

#### 検査は毎回同じ結果になるように作る

並行処理・タイムアウト・後始末を測るlabは、素直に書くと**実行のたびに結果が変わります**。
採点に使えないので、次のどれかで確定させてください。実測して確かめた手口です。

| 測りたいこと | 確定させる手口 |
|---|---|
| 競合状態 | `CyclicBarrier`で一斉に走り出させ、回数を十分に取る（8スレッド×50,000回×20回戦） |
| デッドロック | ラッチで「両方が1つ目のロックを持った状態」を作ってから2つ目へ進ませる |
| 再試行の回数 | clientの自己申告ではなく、**受け取った側**が数える（`/counts`のような口を作る） |
| プールの終了漏れ | 別JVMで使って閉じ、**そのJVMが自力で終了するか**をプロセスの生存で見る |
| 接続の閉じ漏れ | `max_connections`を下げて、**枠を使い切るか**で見る |

#### 目標の検査と、見張りの検査を分ける

`sourceChecks` と同じ区別が `runtime-lab` の `checks` にもあります。**足すときにどちらなのかを決めて、
ラベルに書いてください。**

- **目標の検査** … 学習対象を測る。**ひな形のままでは必ず落ちる**
- **見張りの検査** … 「間違った直し方」を止める。**ひな形が満たしていてよい**

見張りが必要になるのは、いちばん短い直し方が別のものを壊すときです。実際にこうなっています。

| 章 | 見張り | 止めたい直し方 |
|---|---|---|
| 23-5 | `session-continuity` | かごを要求属性へ移す（次の要求に残らない） |
| 24-4 | `jdbc-crud` | プレースホルダへ移すときに問い合わせを壊す |
| 27-3 | `tx-crossing` | 1つのトランザクションにまとめた結果、取得順が交差して待ち合わせる |
| 28-4 | `rest-public` | 全部に`@RolesAllowed`を付けて、公開すべき場所まで閉じる |

見張りはラベルの先頭へ`（見張り）`と書き、問題文でも「これはいまも通っています。直す対象ではなく
見張りです」と明示します。**「直すべきN件」として並べないでください**（ひな形を測る意味は無いので、
学習者は「何もしていないのに通った」と受け取ります）。

目標の検査にできるなら、そのほうが良いです。29-5では当初`validation-accepts`が見張りでしたが、
ひな形が作成を200で返すように変えて、「201を返す」を実際の直しにしました
（`Response.ok`と`Response.status(CREATED)`の違いは、それ自体が学習対象です）。

**「壊れた版が壊れること」を検査にしないでください。** 直した版が常に正しいことを測り、
壊れた版の観測結果は`FACT`行として結果に出すだけにします。逆にすると、たまたま競合しなかった
実行で「壊れているのに合格」が出ます（実際に、逆向きの同時送金で残高一致まで条件に入れたところ、
ひな形が5回に1回通りました。条件から外して直しました）。

接続の閉じ漏れを`pg_stat_activity`の本数で測るのは**うまくいきません**。参照が切れた接続はGCで
回収され、ソケットも閉じられるので、数える時点には消えていることがあります（8本漏らした直後に
残っていたのは5本、`System.gc()`のあとは0本でした）。本番で表に出るのと同じ形——枠を使い切って
`too many clients already`になる——で測ります。

足場（harness）側も、学習者の実装に引きずられないようにします。プールを終わらせない実装を
測るJVMは自分も終了できないので、測定の最後は`System.exit(0)`で落とします。DBの枠を使い切る
実装を測るときは、足場自身の接続も取れなくなるので、場面ごとに例外を捕まえて次へ進めます。

Native Imageのように環境負荷が高く、すべての学習者へ必須にすべきでない発展演習は、taskへ
`"required": false`と`"kind": "applied"`を指定します。採点・下書き保存・模範解答は通常問題と同じですが、
章クリア、★、カフェ報酬、復習出題、全問題完走の分母には入りません。任意問題だけtimeoutを最大600秒まで
設定できます。単に難しいという理由では任意にせず、特別なOS・container・大きなdownload・長いbuildなど、
本筋の到達を妨げる環境条件がある場合に限ります。

`quiz` の `answer` と `explanation` はブラウザへ渡されません。答え合わせは `/api/quiz` が行うので、
**画面のソースを見ても正解は分かりません**。`answer` が選択肢の範囲外だと起動時にエラーになります。

クイズを足すときは、**Javaを知らなくても解けてしまう手がかりを作らない**ようにします。
3つ見つけて潰しましたが、**そのうち2つはクイズが増える過程で戻りました**（2026-08-15に直し直し、
以後は検査ツールで見張っています）。人手のレビューでは、1問ずつ見ても戻ったことに気づけません。

| 手がかり | 対策 | 現在（401問で実測） |
|---|---|---|
| 正解の位置が偏る | 4か所へ均す | 118 / 105 / 99 / 79（均すと各100）。**直せない**（下記） |
| 正解だけが長い（説明文になっている） | 理由は `explanation` へ移し、誤答を具体化する | 見分けられる差（全角2文字ぶん以上）で長いのは**25.2%**（4択の偶然の水準25%）。全角5文字ぶん以上長いのは1問 |

`./tools/check-quiz-fairness.sh`（1秒）が下2つを見張ります。**長さは文字数ではなく画面上の幅**で
数えます（`Jakarta EE/MicroProfile` のような半角のAPI名を全角と同じ重みで数えないため）。
また**1文字未満の差は数えません**。`void Book(String t) { }` と `Book(int a, int b) { }` の差は

> （正解した記録が誤答になり、復習の苦手度がずれる）。新しく足すクイズで位置を散らすほかありません。

### 解説は誤答を名指しで否定する

正解の理由だけを書いた解説は、**間違えた人に何も返しません**。この教材の標準の形は
「誤答を1つずつ否定してから、正解の理由を述べる」です。選択肢を書き換えたときに解説を
読み直すのは（下の検証表）、この形を保つためでもあります。

```text
✗ クラスやメソッドをURLパスへ対応付けます。                      ← 正解の言い換えだけ
○ DBのパスワードは設定として外から与えるもの、継承元は `extends` の宣言、
  メモリ量は起動オプションで、どれもこのアノテーションで書くものではありません。
  `@Path` はクラスやメソッドを HTTP のURLパスへ対応付ける宣言です。
```

**2026-08-16に92問の解説を書き足しました。** 誤答へ一度も触れていない解説が、後半の章
（`ch45` `ch60`〜`ch63` など）に固まっていました。書き足しても `answer` と `choices` は
変えていないので、進捗の `quizChoices` と手がかりの指標は動きません。
機械で数えられるのは「解説と誤答に共通の語があるか」までで、言い換えで否定している解説と
区別できません（**数えた138問のうち46問は言い換えで足りていました**）。最後は読んで決めます。

**2026-08-15に下2件を直しました。** 391問へ増える過程で戻っていたもので、原因は共通でした。
誤答が「物理サーバー本体」「一通り確認しました」のような投げやりな一言で、**選択肢として
成立していなかった**ことです。Javaを知らなくても消せるので、正解だけが具体的な技術的記述になり、
長さも断定語も正解の側へ偏っていました。そこで誤答を**ありえる誤解**へ書き換えました
（例: 「Open Libertyが提供するもの」の誤答を「物理サーバー本体」から
「JVMとJDKそのもの。サーバーを入れればJavaの導入は要らなくなる」へ）。
**158問・選択肢439件を書き換え**、長さと断定語の両方が同時に基準内へ入りました。
`answer`（正解の番号）は1問も変えていないので、進捗の `quizChoices` はそのまま使えます。
断定語は外すだけでなく、
`List.of` の変更や `null` のアンボクシングのように**Javaが本当に保証すること**は
正解の側で「必ず」と書いています。

`explanation` は **誤答が誤りである理由まで**書きます。正解の理由しか書いていないと、間違えた学習者は
自分の考えのどこが違ったのか分からないままになります（全391問の中央値114字）。

> **誤答を書き換えたら、解説も必ず読み直してください。** 解説は誤答を名指しで否定していることが
> 多いので、選択肢だけ直すと**存在しない選択肢を否定する解説**が残ります。実際に2026-08-15、
> 誤答を158問書き換えたときに解説を28件しか直さず、37問でこの状態を作りました
> （例: 「SQLの暗号化や型消去、GCとは関係ありません」——3つとも消した誤答）。
> 読んだ人には何の話か分からず、手がかりを潰す前より悪い状態でした。

通常の判定は「出力の完全一致」です。加えて`sourceChecks`がある問題では、`switch`や
`@Transactional`など問題で指定した書き方も確認します。これは完全なJava構文解析ではなく、
学習対象を実際に一度は書いてもらうための補助検査です。出力比較では各行の行末の空白と、
末尾の空行を無視します（初心者がつまずきやすく、学習の本題でもないため）。

`sourceChecks` を足すときは、次の2つを満たすようにします。

- **問題文が明示している構文だけを縛る。** 問題文が別の書き方を許しているなら検査を入れません
  （正しい別解を弾くと、学習者は理由の分からないまま落ちます）。書き方を縛りたいなら、
  先に問題文へ「〜で書いてください」と書きます。
- **模範解答は必ず通る。** これは例外なく満たします。`verify-solutions.sh` が確認します。
- **学習対象を測る検査は、ひな形のままでは通らない。** 「その構文を書けるようになる」ことが
  到達目標なら、ひな形が既にその構文を含んでいてはいけません。含んでいるなら、その検査は
  学習者へ何も要求していません。ひな形側は `--strict-starters` を付けたときと、構成検査つきの
  問題で `verify-solutions.sh` が確認します。
- **足場の見張りは、ひな形が満たしていてよい。** ひな形が `class Rectangle` や `int area()` を
  与えていて、検査の目的が「与えた宣言を消したり改名したりしていないこと」なら、ひな形が
  最初から満たすのが当然です。これは学習対象の検査ではなく、提出物の形を保つための見張りです。
  足すときは、どちらの目的なのかを自分で決めてから足してください。

テキストブロックや文字列・コメントの中身は検査の前に空白へ置き換えられるので、
`"""` やリテラルの中身は `pattern` で数えられません（外側の `.formatted(...)` などを見ます）。
「`case LOW_STOCK` を書く」のような**構造**は検査できますが、「`"残りわずか"` と表示する」のような
**文言**は検査できません。文言はテストケースの出力比較で確認します。

現在 `sourceChecks` は **621件**あり、276問で使っています。
出力比較だけで十分な問題には付けず、学習対象の構文を実際に書いたか確かめられる場合だけ使います。
正規表現が模範解答で本当に成立するかは `tools/CheckCount.java` で確かめられます。これは採点と同じ
`jq.judge.SourceChecker.codeOnly` と同じ正規表現フラグを使ってヒット数を数えるだけの道具なので、
数分かかる `verify-solutions.sh` を待たずに、書いた検査の当たり外れが分かります。

ひな形の側は `./tools/check-source-checks.sh` が全件まとめて数えます。サーバーを立てないので
数秒で終わります。`verify-solutions.sh` が見るのは「ひな形が**全体として**合格しないか」なので、
検査が複数ある問題では1件が空振りしていても他が落ちて隠れます。この道具は1件ずつ数えるため、
その隠れた空振りが出ます。`--baseline N` を付けると、N件を超えたときだけ失敗します。

要求（`minimum>=1`）でひな形が満たしている検査は現在 **84件（56問）** あります。多くは
`class Rectangle` や `int area()` のように**ひな形が与えた宣言**を見張るもので、
「学習対象を書いたか」ではなく「与えた足場を壊していないか」を見ています。上の規則は前者を
想定した書き方なので、後者を新しく足すときは、それが見張りであることを承知して足します。
禁止（`minimum=0`）はひな形が満たすのが正常なので、この数には入れません。

**別解を弾いていないか**は、模範解答が通ることとは別に確かめる必要があります。「`Arrays.sort` を必須にすると
`Collections.sort` で書いた正解が落ちる」ような縛りは、学習者から見ると理由の分からない不合格になります。
上の1つ目の規則がそれで、迷ったら検査を足さずに出力比較へ任せます。

### ファイルを作る問題を書くとき

提出1回につき **コンパイルは1回だけ** で、そのあとテストケースの数だけ実行します。
作業ディレクトリはケース間で共有されるので、**あるケースが作ったファイルは次のケースにも残ります**。

そのため、ファイルを扱う問題は必ず「まず書く（`writeString` / `write` は上書き）」か
「まず消す（`deleteIfExists`）」から始める形にしてください。`APPEND` だけで組み立てると、
ケースの順番や回数で結果が変わり、採点が安定しません。「まだファイルが無いこと」を
前提にした出力（最初の `exists` が `false` など）も同じ理由で避けます。

### 解説に出力を書くとき

解説の中で「この式はこう出る」と書いた値は、`./tools/check-explanation-output.sh` が実際に実行して
照合します。照合できるのは次の形です。

```java
System.out.println(9 / 10);     // 0
System.out.println(1.0 / 3);    // 0.3333333333333333
"istanbul".toUpperCase(Locale.ROOT);   // ISTANBUL
```

- 値のうしろへ説明を続けるときは、**2つ以上の空白で区切る**（`// 3     わる` は `3` を値として読む）。
  `// 10日後` `// import 不要` のように区切りが無いものは説明文として扱い、照合しません
- **前の行も含めてそのまま実行する**ので、`int n = 7;` のような前置きは同じブロックへ書きます。
  別のブロックの変数を使う断片は実行できないので、照合の対象から外れます（数には出ます）
- `class Main` を含む完結したプログラムの直後に出力ブロックを置くと、出力全体を照合します
- 実行しないもの: 入出力・時刻・乱数・スレッドを含むブロック、くり返しの中の行、
  `Point@1b6d3586` のようなハッシュを含む値

**照合できる組を増やしたいときは、断片ではなく動く形で書きます。** どれが照合できていないかは
`--skipped` で一覧できます。

### 図を入れる

解説の中に図を置けます。` ```svg ` のブロックにSVGを書くと、キャプション付きの図として出ます
（開始行の `svg` のうしろに書いた文字がキャプションになり、そこではマークダウンも使えます）。

````
```svg 変数が持っているのは「本体がどこにあるか」だけ
<svg viewBox="0 0 720 120">
  <rect class="fig-box" x="20" y="30" width="150" height="40" rx="6"/>
  <text class="fig-t fig-code" x="34" y="50">Point a</text>
  <line class="fig-line" x1="176" y1="50" x2="300" y2="50" marker-end="arrow"/>
</svg>
```
````

決まりは3つだけです。

1. **色は書かない。** クラスで当てます（`fill="#fff"` のような指定は落とされます）。ライト／ダークの切り替えに図も自動で追従させるためです。
2. **`id` は書かない。** 同じページに図が何枚も並ぶので、矢印に必要な `id` は変換側が図ごとに振ります。
3. **矢印は `marker-end="arrow"`** と書きます。`arrow` / `arrow-accent` / `arrow-ok` / `arrow-ng` の4種で、`marker-start` も同じです。

使えるクラスはこれだけです（`web/style.css` の「解説中の図」の節）。

| 用途 | クラス |
|---|---|
| 箱 | `fig-box` `fig-box-plain` `fig-box-accent` `fig-box-ok` `fig-box-ng` `fig-box-dim` |
| 囲い・塗り | `fig-region`（破線の枠） `fig-fill` `fig-fill-accent` `fig-fill-ok` `fig-fill-ng` `fig-fill-dim` |
| 線 | `fig-line` `fig-line-accent` `fig-line-ok` `fig-line-ng` `fig-line-soft` `fig-dashed` |
| 文字 | `fig-t`（基本） `fig-t-dim` `fig-t-faint` `fig-t-ok` `fig-t-ng` `fig-t-accent` `fig-title` `fig-small` `fig-mono` `fig-code` |

- `viewBox` は必須です。**幅は700〜760** で描くと本文の幅に合います（`.lesson-view` が860px）。
- 表示寸法は `viewBox` から決まり、**縮小しません**。狭い画面では表と同じく図の中だけが横スクロールします。
- `fig-t` に `dominant-baseline: middle` が入っているので、`y` は文字の **中心** で指定します。
- 使えるのは `g rect circle ellipse line polyline polygon path text tspan title desc` と座標・書式の属性だけです。
  それ以外（`<script>` `<image>` `<a>` `onclick=` など）は取り除かれます。
- **書き間違えると図にならず、コードブロックとして表示されます**（黙って消えないので、画面を見れば気づけます）。
- ` ```svg ` は**行頭から**始めてください。段落の途中に差し込むと、フェンスとして認識されずに崩れます。

### 問題を1問足す

レッスン直下（`task` 〜 `solution`）が **1問目**、`extraTasks` の各要素が **2問目以降** です。
`extraTasks` を書かなければ1問だけのレッスンになります。各要素の `kind` は
`practice`（練習問題）/ `drill`（ドリル）/ `applied`（応用）のどれかで、見出しのバッジに出ます
（省略すると `practice`）。

進捗は `レッスンID#連番` で保存されます（`5-2#1` が1問目、`5-2#2` が2問目）。連番は
「レッスン直下 + `extraTasks` の並び順」で決まるので、**`extraTasks` は必ず末尾に足してください**。
途中に挿入すると番号がずれて、すでに付いている ★ が別の問題のものになってしまいます。

問題を足すときの目安は「**解説で教えたことには、必ず対応するアウトプットがある**」状態です。
解説とサンプルが教えている論点を並べ、1問目が実際に手を動かさせている論点を引いて、
残ったものを2問目で問います（残りが無ければ、サンプルを1か所変えるだけの `drill` にします）。
数を増やすこと自体が目的にならないように、この基準に合わない問題は足さない方がよいです。

`single-file` の `starterCode` は **それ単体でコンパイルできる** ようにしてください（学習者が書く
部分はコメントで示します）。「学習者がこれから書くクラス」を参照するひな形は、
`verify-solutions.sh` で落ちます。`artifact` の `starterContent` は対象形式として解析できる状態にします。
`project` はひな形の検証コマンドが起動でき、模範解答の全ファイルを入れると成功する状態にします。

### 章を1つ足す

1. `content/ch57-xxx.json` を作る（既存のファイルを写すのが早いです。番号は既存と重ならないものにします）
2. `content/manifest.json` で、所属させたい編の `chapters` にファイル名を足す

追加前に「この章を終えると何ができるか」と「直接必要な前提章」を1行ずつ書き、**最後の前提章より後、
その知識を初めて使う章より前**へ置きます。前者はそのまま `objectives` になります（「到達目標を書く」）。
所属は次の基準で決めます。

| 編 | 置く内容 |
|---|---|
| Java基礎 | どの進路でも使う文法、オブジェクト指向、基本ライブラリ |
| Java実践・開発基盤 | 標準API、JDKツール、テスト、DB・HTTPの基礎、チームへ渡す開発作法 |
| JVM・並行処理・性能 | 実行時の仕組み、並行性、I/O、計測と性能改善 |
| Web・Jakarta EE | HTTPとJakarta標準による業務Webアプリ設計 |
| 業務フレームワーク | Spring Boot、Open Liberty、Quarkusなど製品固有の開発・運用 |
| 本番運用・セキュリティ | 実DB・非同期連携、障害耐性、配備、監視、認証・認可とAPI契約 |
| 業務アプリ総合演習 | 前の編で学んだ知識を組み合わせる改修・調査。主要な新概念は増やさない |

比較章は製品別の章より先に、複数編で使う概念は最初の利用箇所より前の共通編に置きます。
1章の主目的が「AとB」の2文に分かれるなら章を分け、逆に単独では成果物や判断につながらない小項目は
近い章のレッスンへまとめます。

#### 章を2つに分ける

既存の章を分けるときは、次の順で確かめます（`ch54` `ch42` `ch41` `ch52` `ch29` を分けたときの手順）。

1. **レッスンIDは変えない。** 進捗は `progress.json` に `42-3#1` の形（レッスンID＋問題番号）で
   入っていて章IDは含まないので、IDを変えなければクリア記録・復習の重み・書いたコードが残ります。
   逆にIDを振り直すと全部失われます。**前半を元のファイルに残し、後半を新しい章へ移す**と、
   新しい章のレッスンIDだけが章番号と食い違う形（`ch66` に `42-3`）になります
2. **章末演習をどちらへ置くか決める。** 全章が章末演習で終わる作りなので、割ると片方に演習が
   無くなります。既存の演習は**それが多く測っている側**へ残し、もう片方へ新しく3問書きます
   （`ch54` だけは中間演習が継ぎ目にあったので新規作成が不要でした）
3. **到達目標を付け替える。** `objectiveIds` は `<章id>-oM` でなければならないので、移した
   レッスンの目標は新しい章のidへ書き換えます。**残った演習が別の章の目標を測っていたら、
   その問題を書き換える**（測る目標が無い問題は `check-objectives.sh` が落とします）
4. **`libs` を運ぶ。** `libs` は**章レベル**の宣言で、その章の全レッスンが受け継ぎます。
   移したレッスンが `MiniValidator` などを使っていると、`libs` を書き写さない限り
   **コンパイルできません**（`ch29` の分割で実際に踏みました）。`ch22`〜`ch29` が該当します
5. **投資率を測り直す。** 章クリア報酬は「その時点の店の産出量 × 章の問題数 ÷ 4」なので、
   割ると報酬の一部が早い時点（産出量が小さいとき）に支払われ、生涯収入が減ります。
   1章の分割で投資率が約2ポイント上がります（`./tools/simulate-cafe.sh`）
6. 検証は `./tools/check-objectives.sh`・`check-content-inventory.sh`（差し替えた問題の
   ヒントやケースが減っていないか）・`./tools/verify-solutions.sh --only <両方の章>`

画面上の章番号は、各編の `chapters` の並び順で **1から** 自動的に振られます。
既存の進捗を壊さないため、ファイル名とレッスンID（`21-1` など）は保存用IDとしてそのまま使い、
Web・Jakarta EE編の画面では `1-1` のように編内番号へ変換して表示します。
新しい編を作る場合は、`id` `title` `subtitle` `prerequisite` `emoji` `chapters` を持つ要素を `parts` に追加します。

**レッスン番号（`-` の右）も画面では振り直します。** 章の中の位置で 1 から数えるので、
IDが `41-4` から始まる章でも画面は `5-1` から並びます（`web/app.js` の `displayLessonId`）。
IDの番号をそのまま出していたときは `4-1 4-2 4-3 4-6` のように飛んで見え、
学習者には「レッスンが抜けている」と読めていました。**事前確認だけは本編に数えず `-0`** を
割り当てるので、事前確認は章の先頭に1つだけ置きます（`check-chapter-refs.sh` が検査します）。

#### 他の章・他のレッスンを参照するとき

番号が3つある（`chNN` の**内部番号**、画面に出る**編内番号**、編内番号より前に使っていた
**旧通し番号**）ので、書く場所によって使い分けます。`./tools/check-chapter-refs.sh` が検査します。

- `content/*.json` の本文からは、**内部番号**で `第NN章` と書きます。`web/app.js` の
  `localizeChapterReferences` が `chNN` の章を引いて編内番号へ読み替え、別の編なら編名も
  前に付けるので、章を並び替えても直す必要がありません
- ただし読み替えは `renderMarkdown` を通る本文だけです。`parts[].prerequisite`、
  `sourceChecks[].message`、`samples[].code` は `esc` でそのまま出るので、番号を書かずに
  編名と章タイトルで参照します
- `labs/**/README.md` は**番号を書きません**。READMEはファイルとして読まれ、誰も読み替え
  ないので、`Web・Jakarta EE編『Jakarta EE 11アップデート』の「章末演習：…」` のように
  編名・章タイトル・レッスン名で参照します。**レッスンIDも同じ**です（`62-3` は画面では
  `4-3` と出るので、学習者が探しても見つかりません）。`check-chapter-refs.sh` が両方見ます
- `docs/` は保守者向けなので、ファイルを探せるように `ch45` のような内部番号で書きます。
  編内番号（画面の番号）と同じ文に混ぜないこと

レッスンを指すときも同じで、本文には**内部ID**で `13-5` と書きます。`localizeLessonReferences`
が画面の番号（`14-5`）へ読み替えます。こちらには2つ注意があります。

- **コードブロックの中は読み替えません。** `5-5` の二重ループの出力例が `1-1 1-2 2-1 …` で、
  これはレッスンIDと同じ形をした出力です。読み替えると壊れるので ``` の中は素通しします
- **地の文に数の範囲を `2-3` のように書かないこと。** レッスンIDと同じ形なので読み替えの
  対象になります（「2〜3個」と書きます）。正規表現の `[1-9]` は角かっこがあるので対象外です

### 到達目標を書く

章には「この章を終えると何ができるようになるか」を `objectives` として書き、レッスンから
`objectiveIds` で参照します。**学習者の画面には出しません**（`rubric` と同じく、問題を書く側の
基準として持ちます。「到達目標も問題を書く側の基準」）。

```json
{
  "id": "ch03",
  "objectives": [
    {"id": "ch03-o1", "text": "整数どうしの除算と `%` の結果を予測して書ける"},
    {"id": "ch03-o4", "text": "`printf` と `String.format` で桁や小数点をそろえて表示できる"}
  ],
  "lessons": [
    {"id": "3-1", "objectiveIds": ["ch03-o1"], "…": "…",
     "extraTasks": [{"objectiveIds": ["ch03-o4"], "…": "…"}]}
  ]
}
```

なぜ要るのか。章クリアは「必須問題を全部解いたか」を、`layers`（概念・コード・実践）は
「どの形式まで到達したか」を答えます。どちらも**終わったか**の話で、**何ができるようになるか**は
どこにも構造化されていませんでした（導入文に目標らしい記述があったのは321レッスン中11件）。
`objectives` はそこだけを埋めます。`rubric`（5軸）とも役割が違います。

| 仕組み | 答えること | 画面 |
|---|---|---|
| 章クリア | その章の必須問題を全部解いたか | 出す |
| `layers` | 概念・コード・実践のどの形式まで到達したか | 出す |
| `rubric` | 説明・実装・診断・テスト・判断のどの能力軸を測ったか | 出さない |
| `objectives` | **その章を終えると何ができるようになるか** | 出さない |

書き方の規則です。`./tools/check-objectives.sh` が機械で見張ります。

- 章あたり **2〜5個**。`id` は **「章のid + `-oM`」**。章のidは `ch03` のような内部番号ですが、
  `30` `32` `34` `37` `38` の5章は旧形式のidなので `30-o1` になります（`ch30-o1` ではありません）
- **可能形で終える**（「〜できる」「〜書ける」「〜選べる」「〜決められる」）。可能形は
  「`る`／`ます` の直前がエ段のかな」なので、検査はその形かどうかで見ます。語尾の一覧を持つと
  書くたびに一覧が伸びて検査の意味が薄れるためです。「〜を理解する」「〜がわかる」「〜を学ぶ」は
  この形にならないので落ちます。可能形に見えても到達を測れない「〜に慣れる」「〜を覚える」
  「〜に触れる」は名指しで落とします
- **その章の問題かクイズで確かめられることだけ**を書きます。読むだけで終わることは書きません。
  どの問題からも参照されない目標は検査で落ちます。**任意発展問題しか測っていない目標も落ちます**
  （任意発展は章クリアの分母に入らないので、全員が通る問題で測っていないことになります）
- 逆に、`objectiveIds` を持たないレッスンも落ちます（事前確認レッスンは対象外）

`objectiveIds` は**レッスンへ書きます**。レッスン内の問題は同じ目標を測ることが多いので、
1,019箇所へ個別に書かせると重複が増えて実態と合わなくなるほうが早いためです。
2問目以降が別の目標を測るときだけ、その問題へ `objectiveIds` を書いて上書きします。
クイズはレッスンの指定をそのまま使います。

> **レッスンに書いた `objectiveIds` は、そのまま1問目の指定になります。** 1問目はレッスンと
> 同じJSONオブジェクトなので、`ContentLoader` が同じ値を読むためです。ここに**レッスン全体の
> 和集合を書かないでください。** 章末演習で「1問目=基本、2問目=組み合わせ、3問目=実践」と
> 分かれているとき、レッスンへ3問分をまとめて書くと、1問目が測っていない目標まで1問目に
> 数えられ、画面の分母（`0/4問` の4）が膨らみます。**書くのは1問目が測るものだけ**です。
> 総合演習のlabのように1問目が本当に複数を測るなら、複数書いて構いません。
>
> この誤りは検査では捕まえられません（1問目が広く2問目以降が狭いのは正しい書き方で、
> 構造からは区別できない）。書くときに気をつけるほかありません。

**紐づけただけでは「深さ」は合いません。** `check-objectives.sh` は目標と問題の対応が**あるか**を
見るだけで、その問題が目標を**どこまで測っているか**は見ません。実際に、目標が
「liveness と readiness を分けられる」なのに問題が両者を1つのステータスへ潰していた例
（`55-3`）や、目標の後半だけ測っていない例（`59-2` の「stack traceを残せる」）が6件ありました
（レビューのF-17）。紐づけを書くときは、**その問題を解いた人が目標の文を名乗れるか**を
自分で読んで確かめてください。目標のほうが問題より広いなら、問題を足すか目標を狭めます。

**名指しした構文・APIは、問題側に現れなければなりません。** 目標が `` `printf` と `String.format` で… ``
のように道具を名指ししているのに、`String.format` を書かせる問題が無い——という状態が
2026-08-16の点検で6件ありました（`ch03-o4` `ch04-o5` `ch09-o3` `ch20-o1` `ch44-o1` `ch47-o2`）。
直し方は3つで、①その語を書かせる問題を足す ②紐づけを直す ③目標文を実態へ合わせる、のどれかです。
`./tools/check-objective-terms.sh` が全件を見張ります（1秒）。表記の都合で一致しないもの
（`remove(int)` のような引数付きの表記、禁止の名指しである「`sleep` で待たない」など）は、
ツールの `ALLOWED` へ**理由を書いて**入れます。

**「説明できる」は、クイズで測るときだけ使います。** 標準入出力の問題は説明文を採点できません。
実際に測っているのは「違いを出力として作り分けられるか」なので、そう書きます。

| 書き方 | 使うとき |
|---|---|
| 〜を説明できる | その章の**クイズ**が説明の中身を問うとき（`ch13-o5` `ch21-o5` `ch24-o4` `ch46-o1` など8件） |
| 〜を見分けられる／予測して書ける | 問題の**出力の違い**で測るとき（`ch07-o4` `ch10-o2` `ch11-o1` など9件をこの形へ直した） |

2026-08-16に、クイズが無いのに「説明できる」と書いていた9件をこの規則で書き直しました。

解決できない `objectiveIds` を書くと、検査ツールだけでなく `ContentLoader` も起動時に止まります
（どのレッスンのどの問題かまで出ます）。

### mini実装の章に書くこと

教材は Servlet・CDI・JPA・Validation・JUnit・JDBC を、`content/lib/` に置いた**学習用の最小実装**
（`MiniWeb` `MiniDi` `MiniJpa` `MiniValidator` `MiniJUnit` `MiniJdbc`）で練習させます。
**書き方は本物と同じ**にしてありますが、挙動は削っています。そこを書かないと、学習者は
「教材でできたこと」を実務でできることだと思い込みます。

miniを使う章には、**そのminiが最初に出てくるレッスンの解説へ** `### ⚠️ ここが本物と違う` を置き、
次の3つを書きます（`ch22` の `22-1` が見本）。

1. **違いの箇条書き**。対応しているものと、していないものを**名前で**挙げる
   （「JUnitの全機能は再現しません」ではなく「`@AfterEach` `@MethodSource` `@TempDir` は無い」）
2. **「書き方（import 文・アノテーション・メソッド名）は本物と同じ」**という断り
3. `💡` **本物でだけ確かめられること**と、実物を触れる場所（`labs/…` とその章末演習）

```bash
./tools/check-mini-labels.sh          # ラベルの有無と3要素を検査
./tools/check-mini-labels.sh --list   # 章ごとの状況を一覧する
```

**中身が事実と合っているかは機械では見られません。** ラベルを書くときは `content/lib/` の実装を
読んでください。§7-7の作業では、そうしたおかげで**「`MiniJUnit` では `@BeforeEach` が動かせない」と
書いた問題文が事実と違うこと**が見つかりました（`MiniJUnit.java` は `@BeforeEach` を実行します）。
「対応していないもの」を名前で挙げる規則は、こういう思い込みを表に出すためのものです。

### 英語のままにする語と、日本語にする語

説明・問題文・ヒント・見出しでは、**同じものを英語とカタカナで呼び分けません**。基準は2つです。

1. **識別子と固有名詞は英語。`` ` `` で囲む。** 問題が読み込む入力値名（`timeout` `poolSize`
   `runtime`）、CIのジョブ名（`build` `deploy`）、アノテーション（`@Timeout`）、設定キー
   （`cafe.orders.timeout-ms`）、製品の機能名（Native Image、Build-time Optimization、
   Dev Services、InstantOn）。**囲めば検査の対象から外れる**ので、迷ったら囲みます。
2. **それ以外の一般名詞・動作はカタカナ。** コンテナ、イメージ、ビルド、タイムアウト、
   ダウンロード、キャッシュ、ポート、ログ、テスト。

見分け方は「**公式がその語を固有名として大文字で書くか**」です。Quarkusの Native Image は書くので
英語、`docker` の container image は書かないのでカタカナ。`jlink` が作るものは
**ランタイムイメージ**（`ch50` `ch51` `ch61` で使っている呼び方。`縮小ランタイム` は
「小さくしたもの」という説明として使い、成果物の名前には使いません）。

```bash
./tools/check-term-consistency.sh          # 散文に裸の英語が残っていないかを検査
./tools/check-term-consistency.sh --list   # 残っている箇所を全部出す
```

**「試験」と「テスト」は書き分けます。** 工程の名前と項目は**試験**（単体試験・結合試験・試験項目・
試験仕様書）、コードで書くものと指標は**テスト**（単体テスト・結合テスト・テスト密度・テストデータ）です。
システム開発ライフサイクル編は工程の話なので試験、`ch45`・`ch68`・`ch69` はコードの話なのでテストに
なっています。同じ粒度を2つの語で呼ぶことになるので、`70-2` の「『単体試験』は粒度の話」で
**同じものを指すと明記してあります**。`check-term-consistency.sh` は英語とカタカナの対だけを見るので、
この対は機械では出ません。

**なぜ揃えるか。** 初学者は「コンテナ」と「container」が同じものだと確信できません。教材の中で
呼び分けが混ざると、別概念かどうかを毎回考えることになります（2026-08-15の実測では
`container` 41% / `image` 39% / `timeout` 49% が混在していた。レビュー08-14の §7-4）。
**コードと `` ` `` の中は数えません**——そこは英語が正しいためです。

### 追加したらコードを整形する

`samples` と `single-file` 問題の `starterCode` `solution` は「読んで覚える見本」なので、1行に詰め込まれた状態で
残しません。JSONに書くときは1行で書いてしまってもよく、あとから次で整えられます。

```bash
./tools/format-content-code.sh            # 詰め込まれているものだけ整形して書き戻す
./tools/format-content-code.sh --check    # 書き戻さず、対象件数だけ見る
```

**ブロックの `{` が1行に2つ以上あれば、長さによらず詰め込みと判定します。**
`public class Main {public static void main(String[] args){/* TODO */}}` のように**宣言だけ**を
詰めたひな形は文が0個なので、長さと文の数の条件では拾えませんでした（実際に3件見落としていた。
2026-08-16に判定を足した）。配列初期化子とラムダの `{` は数えません。

**字下げの最小単位が4桁より小さいコードも詰め込みと判定します。** `ch22`・`ch23` のServletのひな形が

- **もう一度整形しても変わらない**（冪等）

#### ひな形が落ちることも検査する

模範解答が通ることだけを見ていると、**絶対に落ちない検査**を書いても気づけません。実際にこの穴で、
index名の綴りが違って誰も合格できない検査、要件に書いたのに測っていなかった条件、リークしている
実装でも通ってしまう実測が見逃されていました。

そこで回帰では、`artifact`・`project`・`runtime-lab`のひな形を提出し、**合格しないこと**も確かめます
（追加の実行費用はありません。もともとひな形を提出しているので、その結果を見るだけです）。

`single-file`は既定ではコンパイルの確認だけです。ひな形も全ケースで採点したいときは
`--strict-starters` を付けます。所要はおよそ2倍になるので、採点条件を書き換えたときに使ってください。

全件を回したときは、失敗0件だけでなく「注意」の中身まで読みます。「注意」は環境不足で省略した
問題で、実装の誤りとは別物です。**ただし「省略」は「環境があれば通る」を意味しません。**
長く省略され続けた `62-5#3` は、Dockerを用意しても失敗する状態でした（labが `-Dnative` を渡して
いたが、pomに `native` プロファイルが無いため**mvnは成功したままJVMのjarだけを作っていた**）。
**省略が続いている問題は、環境を用意して一度は中身を走らせてください。**

`check-learn-ui.sh` は**画面のJSでしか起きない壊れ方**を検査します。ブラウザ（Chrome）で
`1-1` を開き、誤答 → コンパイルエラー → ヒントを全部開く → 模範解答をエディタへ入れる →
正解して★とコインと通知を受け取る → 読み直して自動保存を確かめる → 復習の一覧から
解き直しへ入る、までを実際に操作します。採点そのものは `verify-solutions.sh` が見ているので、
ここが見ているのは「サーバーの応答を画面がどう扱うか」です ― 採点結果の描画、
提出の応答（`delta` / `newStar` / `cafeAward`）の受け取り、`applyDelta` の上書き、
報酬の通知、復習がひな形から始まること。**画面の再読み込みで `/api/state` から直ってしまうため、
`delta` の欠けは手で触っても気づけません**。そこで画面が受け取った応答そのものも確かめます。
Chromeが無い環境では省略して成功扱いにします（`check-cafe-ui.sh` と同じ扱い）。
`web/app.js` を触ったら走らせてください。

`check-review-schedule.sh` は復習の出題を決める土台を検査します ―「初クリアの翌日が最初の
期限」「正解で 1→3→7→14→30→60→120日 と伸びる」「同じ日に失敗してから通したら1段戻る」
「失敗だけでは期限が動かない（期限切れのまま残る）」「旧ファイルの苦手度を4倍して読み替える」。

`simulate-cafe.sh` は本番と同じ `ProgressStore` で全問クリアを再現し、設備・自動営業・アイテム・
店舗・終盤改装を安い順に買い切れること、自動売上が毎分学習報酬の5%、
次の★まで5問分の上限を超えないことを確かめます。
**問題数を増やしたときは必ず走らせてください**（1問あたりの報酬が積み上がるので、
教材を増やすとそれだけで投資率が下がります）。

試算は2シナリオを回します。効果が「学習の仕方」に依存する要素（今日の1杯目、復習が育てる
ブランド倍率）は、片方だけでは0と読まれてしまうためです。

| シナリオ | 内容 | 判定 |
|---|---|---|
| plain | 同じ日に一気に完走し、復習しない | 投資率 **25〜45%**。バランスの下限 |
| reviewer | 7日連続で通い、全問を復習・全クイズを解き直す | 投資率 45%以下。復習1問が初回クリア(170bp)を超えないこと |

連続日数は `streak()` が `LocalDate.now()` を見るため直接は作れませんが、直近7日の
`clearDates` だけを書いた進捗ファイルを先に置いて読ませれば作れます。

さらに**買う順番**を4通り試します。設備の★解放条件を外して歯止めが価格だけになったので、
「これを買うのが正解」という一手があると、選択の自由が見かけ倒しになるためです。
安い順（基準）・高い順・抽出力優先・販売戦略優先で完走し、生涯売上が基準の
**0.2〜1.5倍**に収まることを確かめます。現在はどの順番でも 1.00 倍で、順番の差は
ほぼ出ません（上のRankほど1コインあたりの価値が下がるので、深掘りと浅く広くが釣り合う）。

完走時の投資率とは別に、**序盤の解放ペース**（[上](#序盤の解放ペース)）も検査します。
歯止めが価格だけなので、Rank1を下げると数問で6系統すべてが買えてしまい、逆に上げすぎると
何章進めても店が育たないためです。plainシナリオの★1個目から順に設備数を数え、
「★2（1節）では0個」「★6（3節）までに1個」「1章クリアで2〜3個」「2章クリアで5〜7個」を
**上下両側から**確かめます。章の区切りは教材から数えるので、章の問題数を変えても検査はずれません。
Rank1〜5の価格を触ったら走らせてください。

`check-review-economy.sh` は上限そのものを試します ―「今日の1杯目は1日1回」「復習の倍率は
1問1回」「復習で戻る枠は既定の5問分より広がらない」「設備費の割引は合計40%で止まる」。
ここが崩れると無限に稼げてしまうので、復習まわりを触ったら必ず走らせてください。

調整つまみ（価格・倍率・上限）は `src/main/java/jq/progress/CafeEconomy.java` の先頭に並んでいます。
「何が存在するか」（設備・アイテム・自動営業の一覧と効果）は `CafeCatalog.java`、
進捗ファイルへの保存は `ProgressStore.java` で、**経済のバランスを触るときに読むのは
`CafeEconomy` だけ**です。

問題追加による終盤のコイン余りは、20問ごとに自動追加される改装プロジェクトで受け止めます。
まず `ENDGAME_INVESTMENT_BASE_COST` と改装段階の購入状況を確認し、必須の店舗網そのものが早すぎるときだけ
`EXPANSION_CUBIC_COST` を見直します。既存学習者の次回出店費が急に上がるため、章追加だけを理由に出店係数は上げません。
調整したら `CAFE_ECONOMY_VERSION` も1つ進めます。

### 画面とサーバのやり取り

画面は起動時に `/api/state` を1回だけ取り、以後は操作ごとに返る**差分**で手元の状態を更新します。
★の数や苦手度をweb側で数え直さないので、いつ再読み込みしてもズレません。3つの約束があります。

- **`/api/state` は全カリキュラム**（解説・サンプル・問題文込みで3.4MB。gzipで約0.86MB）です。
  章が増えるほど伸びるので、**取り直すのは起動時だけ**にします。
- **教材の読み直しは、変わったときだけ**行います。編集したらブラウザの再読み込みで反映されますが、
  変わっていない回は `content/` の更新時刻と大きさを見るだけで済ませます
  （`ContentLoader.fingerprint()`。解析は1回0.3〜0.4秒かかるため）。JSONが壊れている間は
  直前に読めた内容を使い続け、直した瞬間に反映されます。
- **差分は「提出した問題のレッスンとその章」だけ**です（`ApiHandler.delta`）。1回の提出で変わり得る
  範囲はそこに閉じています。全章ぶんを並べると、1問の提出やクイズ1問の回答ごとに約160KBを
  送り直すことになります。
- **応答のgzipは `StaticHandler.send` が1箇所で行います**（1KB以上の文字の型だけ）。
  `curl` や検査ツールは `Accept-Encoding` を付けないので素のまま返り、展開は要りません。

画面右上の「進捗リセット」を押すか、`progress.json` を削除してください。

## コードの実行について

提出したコードは、あなたのマシン上で **別のJavaプロセス** として実行されます。
暴走しても学習が止まらないよう、次の制限をかけています。

- 実行時間 **5秒**（超えたら強制終了して「終わらないループかも」と表示）。
  コードが別のコマンドを起動していた場合も、**子孫プロセスまでまとめて止めます**
- メモリ **256MB**
- 出力 **20,000バイト**（超えたら打ち切り）
- コードの長さ **60,000文字**（実行・保存とも）
- 同時に走らせる実行は **4件まで**。実行は1件で最大5秒×ケース数かかるため、
  数を絞らないと画面の表示まで待たされます。溢れたぶんは「混み合っています」と返します
- サーバの待ち受けは **127.0.0.1 のみ**（同じネットワークの他人からは触れません）
- 操作を受け付けるのは **このマシンのブラウザで開いたこの画面から** のみ。
  他のサイトのページから `http://localhost:8123/api/run` を叩いてコードを実行させる、
  という手（CSRF・DNSリバインディング）を `Host` と `Origin`、それに `Sec-Fetch-Site` の
  確認で塞いでいます。待ち受けを 127.0.0.1 に絞るだけでは、リクエストがあなたの
  ブラウザから出ていくこの経路は防げないためです（`src/main/java/jq/web/RequestGuard.java`）
- 外部のページからの **iframe埋め込みも拒否** します（`X-Frame-Options` と CSP の
  `frame-ancestors`）。埋め込めると、透明にして重ねた上からボタンを押させることができます

とはいえ「自分の書いたコードが自分のマシンで動く」ことは変わりません。
インターネットで拾ったコードをそのまま提出するのは避けてください。

**`content/` に置いたJSONは、実行されるコードです。** 解説に添えたサンプルは
「▶ サンプルを実行」でそのまま動きますし、`content/lib/` の `.java` は提出コードと
一緒にコンパイルされます。実行される側には上の時間・メモリ・出力の制限しかかからず、
ファイルの読み書きやネットワーク接続は普通にできます。誰かからもらった章のJSONを
`content/` に置くのは、そのコードを自分のマシンで動かすのと同じことなので、
中身を読んでから置いてください。
