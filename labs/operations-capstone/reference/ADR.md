# ADR: 一覧の問い合わせ方を変える

## 文脈

`orders-2.4.0`（2026-08-12T09:12:58Z 配備）で一覧に店舗名を出すようにした。
実装は注文1件ごとに店舗を引いており、`rows=12` の要求で `queries=13` 投げている。
応答は 40ms 前後から 1.2 秒前後へ悪化した。件数に比例して増えるため、
注文の多い顧客ほど遅くなり、放置すると悪化し続ける。

あわせて、一覧の並び順がAPI契約（新しい注文から）と一致していないことも分かった。
利用側の画面は契約の順を前提にしているため、並びが変わると表示が狂う。

## 決定

必要な店舗をまとめて1回で引く。問い合わせは「注文1回＋店舗1回」の2回に固定し、
注文の件数によらない。返す前に注文IDの降順へ並べ替え、契約の順を実装側で保証する。

## 却下した案

- **店舗名をキャッシュする。** 問い合わせ回数は減るが、店舗名の変更が反映されるまで
  遅れが出る。今回の遅さは「件数に比例して増える」ことが原因で、まとめ取りなら
  遅れも整合性の問題も作らずに解ける。キャッシュは別の問題を持ち込むだけになる。
- **注文テーブルへ店舗名を複製する。** 読みは速くなるが、店舗名の更新を2箇所へ
  書く必要が生まれ、不一致の経路を増やす。今回の規模では見合わない。
- **並び順は利用側で直してもらう。** 契約で約束しているのは提供側なので、
  利用側へ回避を頼むのは筋が違う。契約を守る責任を実装へ戻す。

## 影響

- 問い合わせ回数が件数に依存しなくなる。監視は `queries=` の値が2で安定することで確かめる。
- 移行 V4 は expand（足すだけ）なので、古い版のアプリが動いている間も読み書きできる。
  不要になった列を消す contract 段階は、全インスタンスの入れ替え後に別の移行で行う。
- 並び替えを実装側で行うため、一覧の件数が非常に多い場合はDB側の並びとindexを
  合わせておく必要がある（`ix_orders_customer` は `(customer_id, order_id DESC)` で作ってある）。
