# RUNBOOK: 一覧の遅延とキャンセル失敗

## 検知

キャンセルAPIのエラー率で気づく。最初にエラーが出たのは 2026-08-12T09:14:07Z で、
エラー名は `inventory_timeout`（`POST /orders/{id}/cancel`）。
同時に一覧の応答時間が 40ms 前後から 1.2 秒前後へ悪化している。

監視で見る値は次の2つ。

- `route=POST /orders/*/cancel` の `error=inventory_timeout` の件数
- `route=GET /orders` の `duration_ms` の95パーセンタイル

## 確認

1. 遅い要求のログに `queries=13` が出ている。返した行は `rows=12` なので、
   1件につき1回ずつ問い合わせている（1 + 12）。件数に比例して増えるので、
   データが多い顧客ほど遅くなる。
2. その直前の配備を `deployments.txt` で確認する。2026-08-12T09:12:58Z の
   `orders-2.4.0`（一覧の店舗名表示を追加）が該当する。悪化はこの配備の前後で分かれている。
3. `GET /readyz` が `ready=true dependencies=unchecked` を返している。依存先を見ていないので、
   在庫サービスが落ちていても受け入れ可能と答えてしまう。

## 緩和

- 在庫サービスの一時障害は短時間で回復する（09:21 に自力回復）。キャンセルは
  上限付きの再試行で吸収する。恒久障害は再試行せず、利用者へ理由を返す。
- 一覧の遅延は配備の切り戻しで即座に戻る。切り戻さない場合は、影響の大きい顧客へ
  件数の上限を一時的にかける。

## 切り戻し

`orders-2.4.0` を `orders-2.3.2` へ戻す。判断の目安は次のどちらかを満たしたとき。

- `GET /orders` の95パーセンタイルが 300ms を5分以上超え続けている
- キャンセルのエラー率が5分平均で1%を超えている

DB移行 V4 は expand（足すだけ）なので、アプリを古い版へ戻しても読み書きできる。
移行を戻す必要はない。

## 連絡

- 影響を受けた顧客の窓口へ、対象時間帯（09:13〜09:22）とキャンセル再実行の案内を伝える。
- 在庫サービスの担当へ、`inventory_timeout` の発生時刻と件数を共有する。
- 次の配備判断のため、この記録と ADR を配備レビューへ添える。
