# ヒープとスタックの実測演習

JVM・並行処理・性能編『JVMの実行とメモリ管理』のレッスン「ヒープ・スタック・GCとメモリリーク」が採点に使います。

「解放を忘れた」のではなく「不要な参照を持ち続けている」形のメモリリークを、実際のJVMから
測って直す演習です。必要なのはJDKだけです。

編集するのは次の2ファイルで、`reference/` が模範解答、`HeapProbe.java` は固定の実測です。

| ファイル | 何が起きているか |
|---|---|
| `exercise/RecentOrders.java` | putとgetは正しく動くが、古い注文の参照が残り続ける |
| `exercise/OrderTotals.java` | 再帰で合計するので、深い入力でスタックを使い切る |

## 採点で何を測るか

`java -Xmx128m` で実行し、GCログではなく標準のJMXと標準のエラーを見ます（GCログの形式はJVM
実装で違うため）。

| check | 測るもの |
|---|---|
| `heap-retained` | 2万件（1件2KB）を投入したあと、GC後の使用ヒープが24MB以下か |
| `heap-evicted-collectable` | 追い出した注文が`WeakReference`越しに回収されるか |
| `cache-window` | 直近1000件だけが残り、最古が消えているか |
| `stack-deep-input` | 20万件でも`StackOverflowError`にならないか |

出発点では `heap-retained` が58MB前後になります。上限を付けても、追い出したものへの参照を
別の場所（履歴リストなど）へ残していると `heap-evicted-collectable` が落ちます。

## 実測を書くときの注意

ローカル変数は**スコープの終わりではなく「最後に使った時点」**で到達不能になりえます。測る前に
キャッシュ自体が回収されると、リークしている実装でも「保持していない」と見えてしまいます。
`HeapProbe` は測り終わるまで参照を置き場（`KEEP_ALIVE`）へ入れています。

生成物（`out/`）はコミットしません。
