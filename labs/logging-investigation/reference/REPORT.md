# 注文キャンセルAPI 障害調査

## 概要と影響

2026-08-11T10:02:00Zに受け付けた注文キャンセル要求
（requestId `r-500`、orderId `420`）がHTTP 500で失敗した。
このログだけでは全利用者への影響件数と障害の開始時刻は確定できないため、
同時間帯の`response_sent result=HTTP_500`を集計して追加確認する。

## 時系列と事実

- 10:02:00 gatewayが要求を受け付けた。
- 10:02:01 orderサービスがキャンセル処理を開始した。
- 2026-08-11T10:02:02Z databaseサービスで最初のERROR
  `connection_timeout`、result `POOL_EXHAUSTED`が発生した。
- 10:02:03 orderサービスが`cancel_failed`を記録した。
- 10:02:04 gatewayがresult `HTTP_500`を返した。

Authorizationと顧客の自由入力は調査に不要なため、報告へ転記していない。

## 仮説

エラー以前で最も新しい配備は、10:00:00Zの`orders-2.4.0`である。
この配備で接続プールの設定が変わっていれば、それが枯渇を起こした可能性がある。
配備の差分はまだ確かめていない（検証方法の1で確かめる）。時刻が近いだけでは
原因の証明にならず、DB負荷や依存先障害も候補に残す。

## 検証方法

1. `orders-2.3.0`と`orders-2.4.0`の差分に、接続プール設定の変更が含まれるかを確認する。
2. 同じ負荷を与え、使用中接続数、待機数、timeout数を両設定で比較する。
3. DB側の接続上限、遅いクエリ、同時刻の基盤変更も照合する。
4. 旧設定で再現せず新設定で再現することを確認してから原因を確定する。

## 緩和策と恒久対策

緩和策は、差分に接続プール設定の変更があれば、承認された手順でそれを直前値へ戻し（無ければ`orders-2.3.0`への切り戻しを検討し）、
500率と接続待機数が下がるか監視することである。切り戻せない場合は、
キャンセル要求を制限しつつ利用者へ状況を案内する。

恒久対策は、接続上限との整合を配備前に検査すること、負荷テストへ
接続枯渇ケースを追加すること、接続待機数とtimeout率にアラートを置くこと、
安全な項目だけを出すログテストを追加することである。
