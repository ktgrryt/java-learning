# 業務アプリ総合演習：既存の注文アプリを改修する

完成途中の注文アプリへ「注文キャンセル」を追加するラボです。新しいプロジェクトを一から作るのではなく、
要件、既存コード、テストを読み、必要な場所だけを変更します。

このラボはJDK 21以降だけで動きます。外部ライブラリ、Maven、実DBは使いません。フレームワークやDB製品の
設定ではなく、変更経路、責務、テスト、引き継ぎを一続きで練習するためです。

## 最初の状態

`app/`はコンパイルできますが、キャンセル機能のTODOと未完成のDB移行・PR記録が残っています。
そのため、最初のテスト実行は失敗して正解です。

```bash
cd labs/business-app-capstone
./run-tests.sh
```

失敗一覧は答えではなく、現在のコードと要件の差です。最初から参照実装を見ず、次の順で進めてください。

1. [`requirements.md`](requirements.md)を読む
2. `app/src/test/java/cafe/orders/OrderApplicationTest.java`で受け入れ条件を確認する
3. Controller → Service → Repositoryの順に既存コードをたどる
4. TODOを一つずつ直し、テストを繰り返す
5. DB移行SQLと`PR.md`を完成させる
6. 全テスト成功後、変更理由を自分の言葉で説明する

## 主に変更する場所

| ファイル | 責務 |
|---|---|
| `CancelOrderRequest.java` | 理由と冪等キーの入力検証 |
| `OrderService.java` | 存在・所有者・状態・再送の判断 |
| `OrderController.java` | 業務例外からHTTP相当の応答への変換 |
| `V2__add_order_cancellation.sql` | 既存行と両立する列・outboxの追加 |
| `PR.md` | 変更理由、検証結果、配備・切り戻しの記録 |

既存コードを読む練習なので、ほかのクラスも先に確認してください。テストを通すためだけにテスト側を書き換えるのは
この演習の目的ではありません。

## 完了条件

```text
tests=11 passed=11 failed=0
```

に加えて、次を説明できれば完了です。

- なぜ理由の文字数検査と所有者判定を別の場所で考えるのか
- なぜPAIDを404や500ではなく409相当へ変換するのか
- なぜ同じ冪等キーで注文更新とoutbox追加を繰り返さないのか
- なぜ追加列を最初からNOT NULLにしていないのか
- ログへ残す項目と、残さない項目は何か
- 配備に問題が起きたとき、どこまで安全に戻せるか

## このラボで簡略化していること

`InMemoryOrderRepository.saveCancellation`が、注文更新とoutbox追加を一つのDBトランザクションの代わりに
原子的に行います。冪等キーもServiceのメモリに保存し、同じキーは同一内容の再送と仮定しています。
実システムでは、`@Transactional`などのトランザクション境界、DBの一意制約、永続化された冪等レコードを使い、
キーの利用者・操作範囲と要求内容も照合して、再起動、複数インスタンス、同じキーによる別操作にも耐えるようにします。

HTTPサーバーも起動しません。`ApiResponse`はControllerの変換結果だけを表す教材用の型です。考え方を確認した後、
`labs/frameworks`または`labs/jakarta-ee11`で、採用するフレームワークの実APIへ置き換えてください。

## 参照実装


参照実装を写す前に、差分の各行がどの受け入れ条件を満たすのか説明してみてください。
