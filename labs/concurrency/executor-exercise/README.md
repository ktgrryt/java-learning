# タスク実行 lab

集計jobをプールへ投入して並行に走らせ、制限時間・失敗・終了の始末を付けます。
JVM・並行処理・性能編『タスク実行・非同期処理・I/O』の「リソース境界とブロッキングを理解する」が採点に使います。

```
sh run-runtime-lab.sh
```

依存はありません。JDKだけで動きます（`javac`・`java`）。

## 何をするか

`exercise/ReportService.java` を直します。いまはプールを作るだけで、実際には
**呼び出し元のスレッドで順番に**実行しています。採点は4つを別に測ります。

| 検査 | 測り方 |
|---|---|
| `tasks-parallel` | 4本のプールへ8件投入し、同時に走った最大数と所要時間を実測（逐次なら1件・1200ms超） |
| `tasks-timeout` | 4秒かかるjobを含む4件に600msの制限。間に合った結果と、待たずに戻ったかを実測 |
| `tasks-error` | jobが投げた`IllegalStateException("boom-42")`が、原因を保って呼び出し元まで届くか |
| `tasks-shutdown` | **別のJVM**で使って閉じたあと、そのJVMが自力で終了できるか |

## なぜ終了を別のJVMで測るのか

プールのスレッドは daemon ではありません。終わらせないまま `main` を抜けても
**JVMは終了しません**。これは「アプリが終わらない」「コンテナが止まらない」として
現場に出る形そのままなので、`ExitProbe.java` を別のJVMで走らせて、
本当に終了するかをプロセスの生存で判定します（10秒待って残っていれば失敗）。

`TaskHarness.java`（測定側）は最後に `System.exit(0)` で落としています。
測定用のJVMが同じ理由で終われなくなると、測定そのものが終わらないためです。

## ひな形にある `prestartAllCoreThreads`

`Executors.newFixedThreadPool` のスレッドは、既定では最初の投入時に作られます。
ひな形は構築時に先に作っておくので、終わらせ忘れが必ず「終了できないJVM」として現れます。
Virtual Threads（`newVirtualThreadPerTaskExecutor`）に置き換えるなら、この行は消してください。

## 直し方の手がかり

- `invokeAll` は**投入順**のFutureを返します。結果の順番をそろえるのに使えます
- 制限時間つきの `invokeAll` は、間に合わなかったタスクを**取り消し**ます。
  取り消されたFutureの `get` と、失敗したjobの `get` では投げられる例外が違います
- 失敗は包まれて届きます。包みを剥がして原因を投げ直さないと、呼び出し元は理由が分かりません
- `close` では受付を止め、終了を待ち、待っても終わらなければ止めます

## メソッドの形は変えない

`ReportService(int)`・`collect(List)`・`collectWithin(List, long)`・`close()` は
採点の足場が呼びます。名前・引数・戻り値は変えないでください。中の作りは自由です。
