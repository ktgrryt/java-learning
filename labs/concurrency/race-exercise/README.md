# 競合状態 lab

在庫の集計を8スレッドで同時に呼び、壊れた集計を直します。
第32章の「共有状態を不変条件ごと守る」が採点に使います。

```
sh run-runtime-lab.sh
```

依存はありません。JDKだけで動きます（`javac`・`java`）。

## 何をするか

`exercise/StockCounter.java` を直します。1スレッドなら正しく、同時に呼ぶと壊れる実装です。
壊れ方は3つあり、採点はそれぞれを別に測ります。

| 検査 | 何が起きているか |
|---|---|
| `race-lost-update` | `shipped += quantity` が読んで足して書く3段なので、他のスレッドの結果を上書きする |
| `race-invariant` | `snapshot()` が2つの値を別々に読むので、更新の途中（合計が合わない状態）が見える |
| `race-oversell` | 在庫の確認と減算の間に他のスレッドが同じ確認を通るので、在庫を超えて出荷する |

## なぜ「毎回必ず」壊れるのか

競合状態は普通、実行のタイミング次第で再現しません。それでは採点できないので、
この lab では3つの仕掛けで確定させています。

- `CyclicBarrier` で8スレッドを**同じ瞬間に**走り出させます。ばらばらに始めると、
  速いスレッドが終わってから次が始まってしまい、そもそも競合しません。
- 1スレッド50,000回・20回戦まわします。守っていない実装なら、この回数で必ず取りこぼしが出ます。
- 在庫を「全要求より1,000少ない」数にしておきます。足りない分は断られるのが正しいので、
  確認と更新がばらばらな実装は在庫を超えて出荷してしまいます。

実測では、ひな形は20回戦すべてで3つとも失敗し（取りこぼしは1回戦あたり20万件を超えます）、
模範解答は20回連続で3つとも成功します。

## 直し方

`AtomicInteger` を2本にするのでは足りません。1本ずつは原子的でも、
「在庫を減らしてから出荷を増やす」の**間**に他のスレッドが読めるので、合計が合わない瞬間ができます。

数を1つずつ守るのではなく、**一緒に守らないと意味がない範囲**（不変条件のかたまり）を見つけて、
そこを1スレッドずつ通します。読み出しも同じ範囲に入れます。

## メソッドの形は変えない

`StockCounter(int)`・`ship(int)`・`snapshot()` は採点の足場（`RaceHarness.java`）が呼びます。
名前・引数・戻り値は変えないでください。中の作りは自由です（フィールドを増やす・持ち方を変えるのも自由）。
