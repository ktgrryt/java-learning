# 再試行と締め切り lab

落ちたり遅れたりするAPIへ、壊れない呼び方で当てます。
本番運用・セキュリティ編『本番で壊れにくい処理と可観測性』の章末演習が採点に使います。

```
sh run-runtime-lab.sh
```

依存はありません。JDKだけで動きます（`javac`・`java`）。採点側が確保した
localhostの動的ポートで、`FlakyServer.java` を実際に起動します。

## 相手（`FlakyServer.java`・参照専用）

| パス | 振る舞い |
|---|---|
| `/transient` | 最初の2回は503。3回目から200（**一時的**な失敗） |
| `/permanent` | いつでも400（**恒久的**な失敗。何度送っても直らない） |
| `/slow` | 4秒待ってから200（打ち切らないと待たされる） |
| `/counts` | ここまでに受け取った回数。検査だけが使う |

## 何をするか

`exercise/OrderClient.java` を直します。いまは1回送って本文をそのまま返すだけです。

| 検査 | 測り方 |
|---|---|
| `retry-transient` | 取得に成功し、**serverが数えた受信回数が3**であること |
| `retry-permanent` | 400でその場でやめ、**受信回数が1**であること |
| `retry-deadline` | 4秒かかる相手を2.8秒未満で打ち切ること |
| `observability-log` | 相関ID・結果・試行回数を含む1行が、実測と一致すること |

## 試行回数は自己申告を信じない

再試行の検査で肝心なのは「**何回来たか**」です。clientが数えた回数をそのまま採点すると、
実際は1回しか送っていないのに「3回試した」とログに書くだけで通ってしまいます。
そこで受信回数は `FlakyServer` が数え、`/counts` から読み出して突き合わせます。

ログの `attempts` も、この受信回数と一致しているかを見ます。
ログが実際と食い違っていたら、そのログは障害調査で役に立ちません。

## 直し方の手がかり

- 失敗を**種類で分ける**。5xxと応答なしは「もう一度なら直るかも」、4xxは「何度送っても直らない」
- **1回ごとの制限時間**（`HttpRequest.timeout`）と**全体の締め切り**は別に持つ。
  1回を短くしても、再試行を重ねれば全体はいくらでも延びる
- 再試行の前に少し待つ。過負荷の相手へ即座に送り直すと、落ちている相手をさらに押す
- 次の待ち時間を足しても締め切りに間に合わないなら、待つ意味がない

定数（`REQUEST_TIMEOUT_MILLIS` = 500 / `DEADLINE_MILLIS` = 1500 / `MAX_ATTEMPTS` = 4）と
メソッドの形は採点の足場が使うので変えないでください。
